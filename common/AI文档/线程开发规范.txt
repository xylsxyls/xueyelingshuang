CTaskThreadManager、Semaphore与LockFreeQueue使用说明
核对日期：2026-09-10；交互线程架构补充：2026-09-11
本文按仓库当前源码说明实际行为；接口大小写以头文件为准，不能按名称猜语义。配套阅读《工程开发规范.txt》《AI代码开发规范.txt》《仓库使用说明文档.txt》。新建线程统一通过CTaskThreadManager管理，不在业务代码直接new std::thread。

一、职责和依赖
CTask描述一项工作；CTaskThread拥有一个实际工作线程和按优先级分组的任务队列；CTaskThreadManager管理多个CTaskThread的创建、查询和回收。它不是自动把任务分发到任意空闲线程的通用线程池，业务需要选定threadId。
CTaskThreadManager依赖Semaphore，内部用signal/wait唤醒工作线程。业务可再用Semaphore等待任务结果或唤醒长期任务。LockFreeQueue是独立的多生产者、单消费者数据队列，不创建线程、不提供等待或取消。
入口：CTaskThreadManager/CTaskThreadManagerAPI.h、Semaphore/SemaphoreAPI.h、LockFreeQueue/LockFreeQueueAPI.h。通过before脚本准备依赖，不直接包含tools头文件。VS链接依赖由各库API入口处理。

二、选什么业务模型
1. 独立有限任务：导出、离线计算、解析文件、批量处理。每项业务一个Task，完成后DoTask返回。同线程同优先级按投递顺序执行；不共享可变状态的工作可放不同threadId。
2. 最新意图优先：搜索、图片预览、拖动定位、AB端点移动。后续操作使前一结果过期，任务必须有取消标记及请求序号。根据业务停止旧任务后投递新任务；松键、失焦、换媒体也需要明确取消路径。已取消任务禁止再更新画面或业务状态。
3. 长期服务：持续音频送设备、消息接收、按序数据消费。一个Task在DoTask中循环，配合Semaphore和LockFreeQueue；StopTask设置退出标记并唤醒等待。此时任务管理器只知道这个长期Task，不知道内部队列的每项数据。不能期待StopCurTask自动识别或丢弃内部某类业务命令。
4. 高频绝对位置预览：允许用一个常驻Task加唯一待处理位置。新请求覆盖待处理位置并递增代次，解码过程中检查代次。这能避免每次鼠标移动分配Task，但必须明确这是业务自身实现的合并模型。
5. 保序业务：事务、文件写入、资源打开关闭等，不能无差别StopAllTask。先区分不可丢操作、可替换操作及有副作用后不能简单重做的操作。
6. 临时并行批次：为独立分组创建若干threadId，投递有限任务，在独立生命周期协调线程用WaitForEnd收敛（不能使用GUI或关键逻辑线程），然后读取独立结果。
相对操作“向右一步”不能机械等价于绝对操作“定位到时间T”。连续长按可限制为一个在途移动，完成后允许下次重复事件；松键取消剩余连续操作。一次短按应保留其一步语义。

三、创建、投递和释放
在main正常运行阶段先显式执行CTaskThreadManager::Instance()。不要在DLL全局变量构造期间创建线程。
uint32_t threadId = CTaskThreadManager::Instance().Init();
threadId为0表示未取得线程；Init也可能因内存分配或线程创建失败抛异常，初始化边界必须处理并回收此前成功创建的线程。
std::shared_ptr<CTaskThread> thread = CTaskThreadManager::Instance().GetThreadInterface(threadId);
使用前判空。thread是短期操作句柄，不要长期保留导致管理器移除后资源仍被引用。
thread->PostTask(task, 1);
task为std::shared_ptr<CTask>，非空，优先级至少1。数字越大优先级越高。同优先级任务不会自动打断当前任务。高优先级任务会调用当前任务StopTask，但仍须等当前DoTask返回后才能执行。
PostTask当前返回void，空任务、非法优先级、线程退出时会直接返回，不提供成功确认；分配队列节点也可能抛异常。业务必须禁止关闭后继续投递，提交接受和执行成功应分开表达。不能捏造PostTask的bool返回值。
禁止SendTask，它同步等待任务释放，会阻塞调用方；普通业务避免TryPostTask，因为未获得锁就可能拒绝本次请求。命令处理不能靠无休止重试挤占GUI。

四、协作取消的正确实现
以下片段属于某个具体业务Task，类声明放XxxTask.h，函数实现放XxxTask.cpp，不把class写进.cpp。
成员：std::atomic<bool> m_exit; Semaphore m_wake;
构造初始化列表：m_exit(false)。每个新Task使用新的退出标记；不得复用已经被取消的Task并把m_exit改回false。

void XxxTask::StopTask()
{
    m_exit.store(true);
    m_wake.signal();
}

void XxxTask::DoTask()
{
    if (m_exit.load())
    {
        return;
    }
    while (!m_exit.load())
    {
        // 获取本次工作；实际实现不能在此持锁等待其他线程
        // 解码或计算前、过程中安全检查点、转格式前均检查m_exit
        // 最终提交前再次校验m_exit和请求代次
        m_wake.wait(20);
    }
}
上例只示意退出与等待，不是可直接交付的业务实现。有限任务不需要while或Semaphore就不要添加；有必须通知的取消结果，应先完成通知再返回。资源已取得后不能直接return而遗漏释放，应通过确定的清理路径结束。
StopTask应快速、可重复、线程安全；管理器会持有内部锁调用它。不得在StopTask里WaitForEnd、Uninit、回调同一任务管理器或等待DoTask完成，避免锁反转或自等。
取消是协作式，不会强杀线程。外部不可中断的单次调用返回后要立即检查；能接入底层取消回调就接入。视频解码可在转BGRA前检查，取消后省去无用转换；转换完成后仍需检查，避免旧画面发布。
检查标记与发布之间仍有竞争窗口。对严格要求“取消返回后绝无旧提交”的业务，需设计发布锁或代次校验，由接受输出的一侧验证；不能仅凭一个if宣称原子取消。

五、StopCurTask、StopTask、StopAllTask与重做
StopCurTask()通过std::atomic_load取得当前任务的局部强引用后通知，不主动获取m_mutex，不处理等待队列；适合独立预览线程上只有一个在途任务、排队策略已受控的情况。
StopTask(taskId, taskLevel=0)按任务类别ID通知当前及指定优先级/所有优先级中的同ID任务。taskId是业务分配的类别，不是管理器自动生成的唯一请求序号；需要另设requestSerial表示一次请求。
StopAllTask()对当前及所有排队任务调用StopTask。它不是直接clear队列，也不会等待当前任务退出。排队对象后续仍可能进入DoTask，入口必须检查m_exit后立即返回。大量排队对象仍需遍历和出队，因此不能把无限积压交给StopAllTask补救。
这几个接口操作的是所取得的CTaskThread，不是默认停止整个进程所有线程。不要在共享多个无关业务的线程上无差别停止全部任务。
CTask::ReExecute()已有完整实现，默认false；CTask::Clone()默认nullptr。没有重做需求的派生Task不声明、不定义这两个函数。
只有被高优先级任务顶掉后确实需要从头重做的业务才覆盖二者。当前实现取出任务时调用Clone尝试创建备份；是否因高优先级打断而重新排队还需ReExecute为true；高优先级打断且ReExecute为true时将备份放回原优先级队头。StopCurTask/StopAllTask本身不自动安排重做。
Clone必须复制全部业务参数并重新初始化取消标记、句柄等运行期状态。重做不是断点续跑；已经写文件、扣款或提交外部请求的任务不能无条件重做。若可按最新状态重建下一任务，通常无需ReExecute。

六、临时线程和WaitForEnd
典型顺序：创建threadId；投递全部有限任务；停止该批次生产者；释放短期thread句柄；CTaskThreadManager::Instance().WaitForEnd(threadId)；检查共享结果。
有限批次的调用片段（task为已构造的具体业务任务，调用者处于独立生命周期协调线程，不是GUI或关键逻辑线程）：

uint32_t threadId = CTaskThreadManager::Instance().Init();
std::shared_ptr<CTaskThread> thread = CTaskThreadManager::Instance().GetThreadInterface(threadId);
if (thread != nullptr)
{
    thread->PostTask(task, 1);
    thread.reset();
    CTaskThreadManager::Instance().WaitForEnd(threadId);
}

实际工程必须再补充创建/投递异常的清理与结果检查；不要在失败路径留下已启动线程。
WaitForEnd等待既有任务自然完成、线程退出，并从管理器移除线程。调用后该threadId不可继续投递，下一批重新Init。
长期任务不会自然返回时，先通知该任务停止，再WaitForEnd；不能直接等待一个无限循环。
Uninit(threadId)请求停止当前任务并回收线程，排队任务会被丢弃，不保证执行完毕。任务结果对象的取消/销毁协议必须覆盖这种情况。
WaitForEnd、Uninit、UninitAll都可能阻塞，只用于独立生命周期协调阶段，GUI和关键逻辑线程不调用这些阻塞操作；禁止工作线程等待自己，禁止GUI等worker而worker又等待GUI。
同一threadId由唯一生命周期协调方回收，禁止并发WaitForEnd/Uninit；当前源码不能作为并发回收已受保护的依据。UninitAll不是本项目的退出方案；应用记录自己创建的管理器线程ID，按依赖顺序逐个Uninit，不清理其他实例的线程。
返回后才能释放Task借用的对象、渲染回调目标、Semaphore和队列。共享所有权不替代退出协议。

七、Semaphore实际语义
signal()累加计数并通知一个等待者；wait()消费一个计数，先signal后wait也有效。适合任务结果通知和工作到达唤醒。
wait(timeoutMs)返回是否取得信号。当前实现以steady_clock的固定截止时间循环等待，虚假唤醒不延长总等待预算；实际返回仍受操作系统调度影响。
wait(uint32_t timeoutMs)接收无符号毫秒数，0表示只检查现有计数；无限等待使用无参wait()，不提供-1特殊值语义。
event()/eventAll()是无计数通知，分别notify_one/notify_all；早于eventWait的通知不会保留，等待还可能虚假唤醒。不要直接拿它作为跨时序完成保证。业务需要持久条件和正确的同步协议，单纯先检查atomic再eventWait仍可能丢唤醒；完成通知优先signal/wait。
停止长期等待必须在StopTask里signal。多个消费者不能假设一次signal唤醒全部；按消费者数量通知或使用各自停止通道。
命名进程信号量使用createProcessSemaphore/openProcessSemaphore/processSignal/processWait/closeProcessSemaphore；不要与本进程signal/wait混用。平台实现、命名规则和退出清理有差异，必须实机验证。当前Windows/Linux分支不代表Apple移动端已经通过构建。

八、LockFreeQueue搭配方式
当前模板实现为MPSC：多个线程可push，只有一个执行流可pop。不能多个worker共享队列并同时pop；需要多消费者时换用明确支持的模型或由一个消费者分发。
push(const T&)复制元素，内部会分配内存，可能失败；无锁不代表零分配或绝不阻塞，也不代表无限容量安全。业务设置队列预算和过载策略：拒绝、丢弃过期项或覆盖最新意图，不能无限堆积大图或PCM。
生产者先完成queue.push(data)，再wake.signal()。顺序颠倒会让消费者被唤醒却看不到工作。
消费者wait后取数据，使用while(pop(&item))批量处理时仍逐项检查退出。signal计数可能大于批量消费后的队列项数，额外唤醒应允许空队列，不以此判断错误。
empty()/size()是并发近似统计，不作为资源销毁或严格容量判断依据。pop暂时失败不等于所有生产者已经停止。
clear内部也会pop，因此不能与其他pop同时执行。init/destroy要求没有并发访问；即便clear允许与push并发，也不应拿它代替业务代次取消，否则可能清掉新请求。
队列保存裸指针时不会自动解决指向对象的生命周期；优先有明确所有权的数据或shared_ptr。停止顺序：禁止新提交、停止并收敛生产者、通知并收敛消费者、处理剩余数据、销毁队列和唤醒对象。

九、验收与常见错误
至少覆盖：任务尚未开始就取消；执行中取消；停止时正阻塞；转格式前取消；结果发布后立即换媒体；连续新请求；方向反转；有限批次WaitForEnd；退出时有排队任务；多实例分别关闭。
统计提交耗时、排队量、取消到退出耗时、完成/取消结果、线程与内存回落；不能只检查程序没有崩溃。
常见错误：每次按键都排队且松键不取消；StopCurTask被误认为清队列；停止标记直到DoTask结尾才读；用volatile替代atomic；持锁执行慢IO；基类已有默认函数仍大量复制空重写；把WaitForEnd放GUI事件里；对同一threadId多处同时回收。
所有临时验证代码和日志放src/temp任务子目录，测试退出码与实际结果同时检查。

十、交互主线程、逻辑线程与耗时任务分层
本节为2026-09-11用户明确补充的通用架构要求。此前“非GUI协调线程可等待”不包括本节要求持续响应的关键逻辑线程。

1. 三层职责
主线程负责GUI事件接收、读取必要的输入、命中判断、即时交互反馈和提交Task；按钮对应的业务逻辑一律投递到独立逻辑线程执行。不能因为修改一个值、重置位置或其他操作很快就直接在主线程执行业务。
逻辑线程由CTaskThreadManager创建，顺序处理短小逻辑Task，维护业务状态、校验操作顺序及分派后续任务。逻辑线程区别于GUI主线程，也不能与正在执行长时间解码、下载或持续服务的线程混用。
耗时执行线程同样由CTaskThreadManager创建，负责下载、长视频加载、解码、慢IO、导出等操作。主线程和关键逻辑线程都不得同步等待它们完成。
“不能卡住”落实为不得执行耗时业务、阻塞等待、忙等或无限队列追赶；不把此规则夸大为操作系统硬实时或PostTask完全无锁的保证。GUI绘制本身也要控制成本。

2. 所有按钮业务都异步
按钮回调生成带参数和请求身份的Task并PostTask后返回；主线程不调用同步业务接口等结果。多个按钮及菜单、快捷键触发同一操作时应走同一异步入口，不能靠换触发方式绕开规则。
一个交互可投递一个Task或多个有顺序约束的Task。短步骤可在同一个Task内顺序执行，也可按职责拆分；不要求每个小动作都开线程。
例如重置位置、缩放和倍速：可提交一个重置Task在逻辑线程顺序处理三项，也可在同一逻辑队列提交三个Task。需要作为一个整体时必须避免其他请求插入中间，使用一个组合Task或明确的批次顺序和完成协议。
Qt控件、窗口几何、重绘、焦点、对话框等GUI操作必须在GUI线程执行。逻辑Task产生状态或界面指令，经queued connection/等价异步派发回主线程，主线程只应用呈现结果；禁止工作线程直接调用QWidget。不得把原业务整体包入GUI回调以伪装成异步。
文件选择等必须取得用户输入的模态交互可以在GUI线程等待用户；选择完成后再把路径等数据送逻辑线程。模态嵌套事件循环不代表业务可以同步执行，也不能使逻辑线程等待对话框返回。其他已要求的模态弹窗同样由GUI线程呈现，其业务请求/结果仍异步衔接。

3. 逻辑Task分派耗时工作
例如一个按钮既下载文件又加载另一段长视频：GUI提交操作Task；逻辑Task判断依赖关系，为相互独立的下载和加载分别取得任务线程并投递任务，随后立即返回；两项结果分别异步投递回逻辑线程，再由逻辑线程决定下一步和通知GUI。
若加载依赖下载的结果，不得假并行：下载完成通知逻辑线程后再安排加载。逻辑线程不得用WaitForEnd、Semaphore::wait、future.get、join、sleep轮询或阻塞式Qt调用等待结果。
已有引擎提供独立后台线程和异步接口时，逻辑Task可以直接提交到已有引擎。确认接口只做有界提交、不同步等待；不为套用示例再无条件套一层线程或每次点击新建线程。
临时线程必须有数量限制、取消条件、失败处理和回收方，线程创建失败要回报，不允许丢失业务后假报完成。

4. 大量Task与固定执行线程
任务密集时可固定创建若干CTaskThreadManager线程，由业务调度器按轮询、在途数量或已知任务成本分配；任务量、队列上限、过载策略和线程数可配置。
CTaskThreadManager本身不是自动负载均衡池。不得捏造接口，也不得多个消费者同时pop当前MPSC LockFreeQueue。
有先后依赖或共享非线程安全资源的任务固定到相同执行者，不能为了负载均衡打乱顺序。同一个解码上下文不得被多个执行线程并发使用。
高频可替换意图合并为最新目标；必须保留的相对操作用明确累计或批次协议，不能既无限积压又指望取消兜底。

5. 完成、取消与退出
每次请求区分提交、执行中、成功、失败及取消，带实例/媒体代次/操作序号；慢任务回报结果后先检查是否过期。组合操作只在全部必要步骤成功后报整体成功，部分失败按业务定义回滚或保留可重试状态。
逻辑线程只发出取消、拒绝新请求和清理调度指令。必须阻塞的线程回收放独立的生命周期协调任务/线程，同样用CTaskThreadManager管理；不能把WaitForEnd或Uninit转移到关键逻辑线程就认为满足异步。
GUI关闭先请求异步停止、保持必要对象和事件循环有效，后台收敛任务/回调后再通知GUI完成窗口及Qt资源释放。工作线程不得等待自身结束；多个实例只清理自己资源，禁止对共享进程无差别UninitAll。
Task借用上下文必须活到全部任务和回报收敛；共享所有权不替代生命周期协议，QWidget仍由Qt管理。资源释放不能留下每次操作都泄漏的临时线程。
验证必须分别测GUI提交延迟、逻辑队列响应、耗时执行时其他按钮响应、顺序/过期结果、取消及线程资源回落。未经实际验证不能宣称主线程和逻辑线程绝对零阻塞。

6. 实际完成结果驱动GUI状态（2026-09-11补充，所有交互通用）
按钮按下只表示输入任务。PostTask调用完成、Core异步接口返回成功、请求已进入队列或目标值写入待处理字段，都不表示实际执行成功，不能据此将按钮置灰或把业务显示切换成已完成。
每项操作必须有可关联本次请求的终态结果：成功、失败、取消；拒绝提交也必须回报应用。结果携带实例/媒体代次/请求编号、实际错误及必要实际状态。接口名带Async不代表自动具备完成通知，使用前核对真实契约。
同步Core接口的执行结果可以由独立执行Task取得后异步回报，不能让GUI或关键逻辑线程调用同步接口等待；异步Core接口必须等其真正的完成回报。既无完成通知又无法可靠关联请求时，先补业务/Core结果接口，不用最后错误码、时间推测或碰巧相等的快照冒充本次任务完成。
执行结果先回逻辑线程，由逻辑层核对身份、合并批次结果和处理错误，再通过QObject::connect并明确Qt::QueuedConnection发送给GUI线程；GUI接收函数根据实际结果更新控件。无Qt产品使用等价的主线程异步结果派发方式，Core本身不引入Qt。
重置等组合操作只有所有必要子项实际成功、且没有更新请求使结果过期时，才能报告整体成功并把按钮置灰。任一子项失败、取消、结果不完整或未达到约定后置条件时，不得清除待重置状态；按钮保持可点击重试，并保留准确失败原因。不能在任务尚未完成时为去重而提前把重置按钮置灰；重复点击可在逻辑层合并到当前有效批次，不堆积任务。
已经成功的子项可以呈现真实结果，但不能伪装整体成功；是否需要回滚按业务方案明确，不擅自假设所有组合任务天然具备原子事务。对“接口返回成功但实际值被限制”的场景，按接口合同校验实际结果，不把未达到重置目标记为成功。
即时按压、悬停、拖动目标预览等交互反馈可以显示，但必须与已确认业务状态分开；不能直接改Core快照中的播放状态或倍率来伪造执行结果。
接收结果时拒绝旧媒体、旧批次及旧窗口结果；多个子任务终态只统计一次，不让重复或乱序回报提前完成批次。异常、取消、覆盖旧目标、换媒体和退出同样要按协议结束或取消请求，不能永久悬挂待完成状态。
验收要故意令某一子项失败、限制目标值、延迟/乱序完成、取消并重试，检查按钮是否只在全部成功后置灰，以及旧成功结果不会把后来发生调整的按钮错误置灰。任务入队日志与完成日志必须区分。

7. 每个Task的中断设计与按线程ID有序退出（2026-09-11补充）
所有新建或本轮修改的Task都必须明确中断类别、检查点、资源处理和结果回报；不能统一在入口检查一次就认为支持退出。
可随时协作中断的循环任务：入口、循环、安全耗时步骤之间及结果提交前直接检查成员std::atomic<bool> m_exit；构造初始化false，StopTask中置true，并唤醒本任务可能阻塞的等待。
分段任务：明确哪些小段执行中不能中断、在哪些段间检查m_exit；到安全边界后结束，释放半完成资源并回报取消。
不可中断任务：执行前检查m_exit；进入必须完成的短事务/提交段后完成其必要工作和清理才返回。StopTask仍记录请求，不能强杀线程或跳过必须完成的逻辑；已实际提交成功的操作不得假报未执行。不可中断段必须有明确边界，无法约束的外部IO需要超时/底层取消或如实说明退出限制。
不为单纯读写m_exit再写setExit、getExit、isExitRequested等包装函数。Task内直接m_exit.load()/store()或等价原子访问；内部协作函数需要检查时传入有明确借用期的const std::atomic<bool>*，不通过公开可写成员或friend绕过封装。真正承担资源唤醒/通知的函数按用途保留，底层协议要求的取消回调适配不属于多余getter。
StopTask必须短小、幂等，只置标记并做必要唤醒，不等待本任务结束、不回收线程、不持锁执行外部回调；它可能在管理器内部锁保护期间被调用。标记置true不代表DoTask已经退出。
常驻与临时线程均记录CTaskThreadManager::Instance().Init()返回的管理器ID，连同用途、归属和退出依赖；这不是std::thread::id或系统原生线程ID。原生ID若用于自线程判断单独命名，不混用于Uninit。
退出由单一生命周期负责人拒绝新提交后，按依赖顺序逐个CTaskThreadManager::Instance().Uninit(threadId)，每项完成后清理相应ID/记录。禁止用UninitAll代替有序退出，不对同一ID并发回收，不回收其他实例线程。初始化中途失败也按已成功创建的记录逆依赖回收。
Uninit会请求停止并等待实际线程结束，不会强杀不可中断代码。应用存在GUI和关键逻辑线程时，在独立退出协调任务中依次调用；不能从正在被回收的线程调用自身Uninit。协调任务本身返回后，由其外层拥有者在应用最后受控清理阶段回收对应ID，禁止自等待，也不能留下协调线程永久泄漏。
顺序由生产者/消费者和资源依赖决定，不是机械按ID大小排序。先阻止新任务与新回报生产，再停止使用资源的执行者，最后释放依赖；收敛期间保留回调目标和必要GUI事件循环。不能因某个线程已停就提前销毁其他在途线程仍借用的对象。
逐线程记录退出开始/结束、用途、管理器ID、耗时、当前任务/阶段；日志帮助定位卡在哪条线程，但日志本身不证明无死锁。队列中因关闭未运行的任务也必须被统一记为取消，不能依赖其DoTask一定执行来完成回报。
验证覆盖重置/加载/拖动后立刻关闭、任务尚未开始/循环中/不可中断段退出、初始化部分失败、重复关闭、多实例独立关闭和后台回报恰好到达；测量退出时延并记录不可中断段的实际影响。

诊断日志在业务发生位置直接使用LogManager已有公开日志宏，不新增Logger类、日志转发函数、项目日志宏、日志队列或写入线程；不能为了以后替换日志库提前增加适配封装。当前使用LogManager，未来改用LogSender须另按用户指示实施；不因当前接口同步而自行增加异步包装。
文件、函数和行号统一交给LogManager现有日志宏处理；业务调用处不额外获取、拼接或传入__FILE__、__FUNCTION__、__LINE__，不重复实现日志库已有功能。

高频帧、音频块和鼠标移动避免逐次输出大量重复文本；使用必要的统计汇总或日志库已有频率控制能力，关键错误、请求终态和退出阶段详细记录。控制日志量不等于另造日志模块。第四阶段结合真实播放检查日志开销和定位信息是否足够。
DialogManager、QtControls等基础库不包含日志模块，不依赖日志器，也不以qDebug等直接输出业务错误。失败通过接口返回明确错误码，在头文件const std::map中集中定义中文原因；必要的文件路径、解析位置等动态详情另经结果参数返回，不拼成新的错误码。异步操作通过结果通知返回。上层业务在实际处理结果的位置直接记录日志。无调用的日志模块及其工程引用应删除；有调用的先完成结果通路迁移再删除，不能只删日志而丢失错误信息。

十一、当前任务同步与生命周期边界（2026-09-12源码核对及用户确认）
本节按本次确认的源码和业务约束说明，不代表本轮全部改动已经通过运行测试。CTaskThreadManager是长期使用的基础库，不因假设场景擅自移动锁、扩大锁范围或改造接口；发现问题先列出实际调用路径、并发顺序、触发前提及影响，区分旧行为和本轮引入的变化，按用户授权处理。

1. 智能指针的引用安全与对象状态安全分开处理
不同shared_ptr对象共享同一控制块，不等于可以无同步地同时读写同一个shared_ptr成员。m_spCurTask运行期读取统一std::atomic_load，替换和清空统一std::atomic_store；即使某个写入位置持有m_mutex，只要读取方不拿同一把锁，该写入仍需采用同一原子访问协议，不能只改一处或与普通赋值混用。
先取得局部shared_ptr，再判空并调用任务方法；成员随后被清空，不影响局部强引用保持对象存活。不能先普通读取正在被并发修改的shared_ptr来构造weak_ptr，再指望weak_ptr::lock修复此前的数据竞争。安全取得的weak_ptr调用lock成功后返回的是强引用，其他拥有者释放不会令该强引用变成野指针。
原子shared_ptr仅保护引用取得和替换，不保护CTask内部可变数据，也不保证当前任务、备份和优先级构成原子快照。原子不等于无锁；本机VS2013实现使用内部自旋锁，不得据接口名称承诺性能提升。

2. 按类别停止任务的当前实现与边界
StopTask(taskId, taskLevel)先在m_mutex内收集匹配的排队任务强引用，CollectStopTaskToSet通过传出参数追加到set；它不清空传入集合、不删除队列任务，也不调用任务的StopTask。退出锁后原子取得当前任务，类别匹配则加入集合，最后在锁外遍历通知。
先检查队列再检查当前任务，避免原先先检查当前、后检查队列时，任务在两次检查之间由排队转为执行而被漏掉。同一对象在本次集合内去重，不代表不同停止调用之间只通知一次。当前任务按taskId匹配；taskLevel限定队列搜索范围，保持现有接口行为，不能误写成同时限定当前任务优先级。
集合保存引用而不移除队列项；解锁后、通知到达前，任务可能已经开始甚至完成DoTask。新提交或之后重建的任务不保证被本次集合覆盖。业务依靠协作取消，不得把该接口理解为从队列删除任务、保证任务从未执行或等待任务结束。
StopCurTask自身不获取m_mutex；StopTask(taskId, taskLevel)的任务停止回调在锁外。StopAllTaskUnlock和HandlePostTask的旧调用路径仍可能在外层持有m_mutex时通知任务，用户确认暂时保留；不能据函数名中的Unlock断言调用时没有锁，也不据此自行改造旧路径。

3. StopTask回调只做可并发的停止请求
StopTask可能与DoTask并发，也可能被多个调用方重复调用，甚至在DoTask返回后才收到通知。只修改std::atomic<bool> m_exit等安全停止状态；不得执行vector.clear、释放解码器、销毁共享资源等不能与执行线程并行的业务操作，不等待DoTask、不回收线程、不重入本线程管理器。资源清理由执行线程的退出路径或生命周期负责人完成。
对于已有依赖等待唤醒的任务，保留必要且线程安全的signal，并保证唤醒对象在停止调用期间有效；这不授权在回调中添加业务锁、耗时处理或资源清理。只有标志即可完成取消的任务不额外增加唤醒设施。停止标志直接访问，不额外包装单纯的设置和读取函数。

4. 单工作线程、当前任务和备份的关联
当前只有所属工作线程调用PopToCurTask安装新的当前任务；WorkThread的清理也在同一工作线程执行。外部停止接口取得引用并通知，不替换当前成员。不能凭空构造另一条工作线程在PopToCurTask中同时取走任务的场景。
当前队列删除和清空均由该工作线程完成；停止接口只通知、不删除。在这些前提下，HasTask检查非空后到PopToCurTask后续加锁之间，不会被其他线程清成空队列，保留现有锁位置。如果以后新增外部删除队列或多消费者，必须重新审查，不能直接沿用此结论。
备份的创建、重排及正常清理由m_mutex保护。PopToCurTask无任务分支虽然没有持锁清空备份，但当前调用顺序下前一轮已清理当前任务及备份，首次运行也为空；其他访问备份的路径又受当前任务非空条件约束。因此本轮没有将m_spCurTaskBk改为原子访问；这不是普通shared_ptr可随意并发读写的通用结论。
WorkThread先释放执行用的局部强引用，再按原顺序清理当前成员和备份，避免局部引用把已完成任务保留到Semaphore等待期间。有其他强引用时析构仍可能延后，不得假定在atomic_store清空成员时必然完成析构。

5. 提交与退出必须由业务确定先后关系
当前PostTask、TryPostTask保留在锁外检查m_hasExitSignal的原实现。业务在Uninit前禁止新提交，并确保已经进入的PostTask/TryPostTask调用也已返回，再进行线程回收；仅禁止Uninit返回后新发请求，不等于已经收敛并发提交。需要支持提交与退出并发时，必须另行设计提交接受与关闭同步协议，不能宣称现有锁外判断保证这一点。
Uninit完成后，如果外部仍合法持有shared_ptr<CTaskThread>，对象尚在，PostTask会因退出标志直接返回，TryPostTask返回false；通过已移除的管理器ID获取接口则为空，调用前必须判空。对象已销毁时，不能通过失效裸指针调用后指望退出标志保护。
区别Uninit回收实际工作线程、管理器移除对象引用，以及CTaskThread最后一个强引用释放后的对象析构。外部保留强引用可能延后成员资源释放，不能仅凭成员未立即清空就断言永久泄漏，也不能把Uninit返回理解为所有外部共享对象都已析构。

6. 退出不保证每个任务都收到停止回调
SetExitSignal先置退出标志再通知当时取得的当前任务。可能通知时当前为空，随后工作线程才从队列取出任务，再在第二次退出检查处直接退出；该任务既不执行DoTask，也不一定收到StopTask。队列中被丢弃的任务也不能依赖这两个函数执行清理或完成回报。
按当前实现，第二次退出检查只清空队列，当前成员和备份可以保留到CTaskThread析构；在线程对象确实随后释放的使用前提下，成员会自动释放，不能据此单独认定必须修改库。任务所持资源应具备可靠的析构清理，业务取消结果由统一生命周期协议补齐；停止请求、线程退出和对象析构分别理解。
