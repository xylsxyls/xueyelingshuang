一、测试原则

CookServerTest 通过真实 HTTP 请求检查 CookServer，不以函数调用、旧 EXE 或日志输出代替结果。每条用例检查网络解析、状态码、JSON ok 值、关键字段和实际业务结果。测试期间禁止把目标指向生产服务器：用例会创建账号和 token、执行钱包与菜谱变更、发布视频、写评论/互动，并可能写入 Redis/MySQL。

CookWx源代码检查和Node平台契约回归由CookWxTest执行，不能代替实际小程序运行。触摸、原生遮罩、逐帧解码、WebGL、音频、拖动缓存命中、网络权限和手机性能须在微信开发者工具与目标真机验证；官方工具已编译并显示登录页，但Page.getElement元素查询仍超时，完整界面用例没有通过结论，详见CookWxTest测试文档。

三、构建和运行

1. 使用目标 Windows 工具链构建 src/CookServer/CookServer.sln 的 Release|x64，再构建 src/CookServerTest/CookServerTest.sln 的 Release|x64。VS2013/MSBuild 12 工程依赖与 FFmpeg x64 链接库必须正确。构建记录保存命令、配置、退出码、内部日志、目标 EXE 时间戳和哈希。
2. 将本轮 CookServer 构建结果及其需要的 DLL、CookServer.ini、res 资源部署到隔离测试目录；初始化隔离 MySQL/Redis 或测试存储。确认 5207（或指定测试端口）健康检查指向该实例。
3. 在隔离环境运行 CookServerTest1.0.exe。默认 host 为 127.0.0.1、port 为 5207；可用 `--host=127.0.0.1 --port=5207` 覆盖。单请求超时默认 5000 ms，最大响应默认 5 MiB；视频上传专项会将超时提高到至少 30 秒、响应上限提高到 50 MiB。
4. 默认会执行并发压力测试。`--noStress` 只运行功能用例；压力参数为 `--stressThreads=N` 和 `--stressLoops=N`，程序限制最大 256 线程、每线程最多 100000 次。测试账号前缀可用 `--userPrefix=...` 指定。
5. 用例和压力测试都通过、报告成功写入、服务端无崩溃且测试期间没有数据存储错误，才可标记该批通过。失败用例保留日志和测试数据，以准确原因复现后再修复。

报告默认为 CookServerTest1.0.exe 同目录的 CookServerTestReport.txt。不得将报告生成器配置为覆盖需求文档或开发文档。测试服务若连接了真实或含用户数据的存储，先停下并改用隔离环境。

微信客户端人工验证清单：
1. 视频首次从头播放，确认立即只下载首段约 3 秒；播放到 1 秒附近才请求后续 5 秒。
2. 继续播放时，检查在缓存范围剩余约 2 秒时再预取后续 5 秒；最后一段不越过媒体结尾。
3. 第一次完整播放后拖回已缓存区，确认离线或断网时仍可立即 seek；拖到未缓存区域时只请求该片段，加载结束后继续预取。
4. 同视频第二次播放、重复视频、视频文件更新、切换视频、快速连续拖动、缓存空间接近 100 MiB、存储写入失败、弱网超时和下载取消。
5. 逐帧画面方向/颜色、横竖屏和分辨率缩放、音频与画面同步、循环播放、前后台切换、组件复用和长时间播放内存/发热。
6. 不支持 VideoDecoder/WebGL/音频 API 的基础库错误提示；上传进度、失败重试、用户切页取消、超限文件和发布后公开视频播放。
