Cook做菜软件第二期产品设计文档

一、文档说明
1. 本文档只描述第二期产品设计。
2. 第二期建立在第一期核心做菜流程已经被真实用户验证的基础上。
3. 第二期重点是 Android APP、iOS APP、统一账号、真实权益、商业化基础和内容创作后台。
4. 如果第二期后续需要补充或修改，在本文档最后的“第二期补充和修改”章节追加“第二期 V2.1”“第二期 V2.2”等内容。

二、第二期目标
1. 推出 Android APP 和 iOS APP。
2. 建立跨微信小程序、Android APP、iOS APP 的统一账号体系。
3. 微信小程序默认使用微信账号登录，用户打开后优先走微信授权登录。
4. 第一阶段账号密码注册的老用户可以把微信账号绑定到原 userId，不能因为登录方式升级导致金币、元宝、菜谱和个性化数据丢失。
5. 建立真实订单和权益系统。
6. 建立更稳定的本地提醒能力。
7. 建立菜谱创作者发布、审核和管理基础。
8. 建立视频文件存储升级方案，把第一期服务端本地视频目录逐步迁移到对象存储、转码和 CDN。
9. 建立初步商业化路径，但优先控制合规风险。

三、第二期前置条件
1. 第一期已有真实用户完成做菜流程。
2. 用户反馈证明排程和步骤提醒有实际价值。
3. 服务端接口稳定，CookServerTest 能覆盖主要接口。
4. 已有一批质量较高的系统菜谱。
5. 如果要正式收款，需要准备个体工商户或企业主体。
6. iOS 数字内容收费需要按 Apple IAP 规则设计。
7. Android 根据上架渠道接入合规支付方式。

四、第二期平台规划
1. 微信小程序。
   1. 保持轻量入口。
   2. 保留免费菜谱、广告解锁、做菜排程和步骤提醒。
   3. 不在小程序里强引导 APP 外部付费。
   4. 小程序可以提示“多端版本已上线”，但不与付费解锁绑定。
   5. 默认登录方式改为微信登录。
   6. 新用户首次微信登录时，服务端根据微信 openid 创建或绑定统一 userId。
   7. 已有第一期账号密码用户可以先用账号密码登录，再在账号设置里绑定微信。
   8. 如果用户已经绑定微信，后续打开小程序优先自动微信登录。
2. Android APP。
   1. 支持稳定本地通知。
   2. 支持后台提醒。
   3. 支持离线缓存已拥有菜谱。
   4. 支持更完整的做菜历史。
   5. 根据国内应用商店或渠道规则接入支付。
3. iOS APP。
   1. 支持稳定本地通知。
   2. 支持离线缓存已拥有菜谱。
   3. 支持 Apple 登录。
   4. 数字菜谱、会员、金币等虚拟内容按 IAP 规则设计。
   5. 不做绕过 IAP 的外部支付入口。

五、统一账号体系
1. 服务端建立统一 userId。
2. 第二期微信小程序默认使用微信 openid 登录。
3. 微信 openid、手机号、Apple 用户标识、Android 渠道标识都绑定到统一 userId。
4. 第一阶段的 account/password 登录方式继续保留为备选登录方式和账号找回方式。
5. 用户可在不同客户端看到同一批收藏、购买、广告解锁和做菜历史。
6. 登录状态应支持过期和刷新。
7. 账号合并需要谨慎处理，避免两个真实用户数据误合并。
8. 账号数据包括：
   1. 基础资料。
   2. 登录绑定关系。
   3. 已拥有菜谱。
   4. 已购买菜谱。
   5. 收藏菜谱。
   6. 做菜历史。
   7. 广告解锁权益。
   8. 会员或菜谱包权益。
9. 微信登录绑定规则。
   1. 如果 openid 已经绑定 userId，直接登录该 userId。
   2. 如果 openid 未绑定 userId，且用户选择“新账号进入”，服务端创建新的 userId。
   3. 如果 openid 未绑定 userId，且用户选择“绑定已有账号”，需要先输入第一期账号和密码验证身份。
   4. 绑定成功后，第一期账号的金币、元宝、已拥有菜谱、创作菜谱、个性化配置、关注关系和做菜历史全部保留。
   5. 同一个微信 openid 不能绑定多个 userId。
   6. 同一个 userId 可以绑定多个登录方式，但必须在账号安全页清楚展示。

六、订单和权益系统
1. 订单字段。
   1. orderId。
   2. userId。
   3. productId。
   4. productType。
   5. payChannel。
   6. amount。
   7. currency。
   8. status。
   9. createTime。
   10. paidTime。
   11. refundStatus。
2. 权益字段。
   1. userId。
   2. recipeId 或 packageId。
   3. source。
   4. startTime。
   5. expireTime。
   6. permanent。
   7. status。
3. 权益来源。
   1. 免费系统菜谱。
   2. 系统赠送。
   3. 广告解锁。
   4. 购买菜谱。
   5. 购买菜谱包。
   6. 会员权益。
   7. 运营补偿。
4. 关键规则。
   1. 支付回调必须幂等。
   2. 订单成功后再发权益。
   3. 权益发放失败要可补偿。
   4. 客户端展示付费内容前以服务端权益为准。
   5. 退款后权益要能撤回或标记失效。

七、第二期商业化设计
1. 优先级最高的商业化方式。
   1. 菜谱包。
   2. 会员。
   3. 广告解锁。
2. 暂缓的商业化方式。
   1. 可提现金币。
   2. 作者自动分账。
   3. 用户之间直接交易。
3. 原因。
   1. 菜谱包和会员比可提现金币合规风险低。
   2. 作者自动收益涉及结算、税务、风控和投诉处理。
   3. 平台早期最重要的是验证复购和长期使用，不是马上做复杂金融闭环。
4. 抽成配置。
   1. 后续作者收益默认平台抽成 20%。
   2. 抽成比例必须可配置。
   3. 抽成比例变更必须记录生效时间。
   4. 历史订单按订单发生时的抽成规则计算。

八、内容创作和审核
1. 作者可以创建菜谱草稿。
2. 菜谱草稿必须按结构化字段填写。
3. 作者需要填写：
   1. 菜名。
   2. 分类。
   3. 简介。
   4. 封面图。
   5. 成品视频或图片组。
   6. 食材。
   7. 工具。
   8. 每个步骤的标题、细节、时长、资源、安全级别。
4. 提交后进入审核状态。
5. 审核通过后才进入公开推荐。
6. 审核不通过需要返回原因。
7. 高风险步骤必须重点审核。
8. 低评分菜谱进入复审。
9. 被投诉菜谱可临时下架。

九、第二期后台管理
1. 用户管理。
2. 菜谱审核。
3. 评论审核。
4. 订单查询。
5. 权益补发。
6. 内容下架。
7. 作者管理。
8. 广告解锁记录查询。
9. 服务日志和异常查询。
10. 运营配置。
11. 抽成比例配置。
12. 视频文件管理、转码状态查询和异常文件清理。

十、第二期客户端新增页面
1. 登录绑定页。
   1. 显示当前登录方式。
   2. 支持绑定手机号。
   3. 支持绑定微信或 Apple。
   4. 微信小程序端默认展示微信登录状态。
   5. 如果当前账号来自第一期账号密码登录，页面提供“绑定微信”按钮。
   6. 绑定微信前必须要求用户确认当前账号，避免误把别人的微信绑定到自己的账号。
2. 微信登录确认页。
   1. 新微信用户第一次进入时展示。
   2. 页面提供“创建新账号”和“绑定已有账号”两个按钮。
   3. 点击“创建新账号”后，服务端用微信 openid 创建统一 userId。
   4. 点击“绑定已有账号”后，进入第一期账号密码验证页，验证成功后完成绑定。
3. 订单页。
   1. 显示购买记录。
   2. 显示订单状态。
   3. 支持查看权益。
4. 会员页。
   1. 显示会员权益。
   2. 显示价格。
   3. 显示购买按钮。
5. 菜谱包页。
   1. 显示菜谱包包含哪些菜。
   2. 显示总预计时间和适合场景。
   3. 支持购买。
6. 作者中心。
   1. 显示已发布菜谱。
   2. 显示草稿。
   3. 显示审核状态。
   4. 显示基础数据。

十一、第二期视频存储升级
1. 第二期需要把第一期的服务端本地视频目录升级为可扩展的视频存储方案。
2. 推荐方案为对象存储保存原始视频文件，MySQL 保存 videoId、对象存储 key、播放地址、封面地址、转码状态和审核状态。
3. 第二期支持异步转码，至少生成一个适合移动端播放的 mp4 版本。
4. 第二期支持封面生成，用户也可以手动选择封面。
5. 第二期支持 CDN 播放地址，减少 CookServer 直接承载大文件下载压力。
6. 第一阶段已经上传到本地目录的视频需要提供迁移脚本或迁移任务。
7. 迁移完成后，旧本地文件不能立刻删除，必须等 MySQL 元数据校验、播放验证和备份完成后再清理。

十二、第二期验收标准
1. 同一账号在小程序、Android、iOS 上权益一致。
2. 微信小程序默认微信登录可用。
3. 已有第一期账号密码用户能绑定微信，绑定后金币、元宝、菜谱、个性化配置和历史记录不丢失。
4. 同一个微信账号不能错误绑定到多个 userId。
5. APP 本地通知在授权后能稳定提醒关键做菜节点。
6. 支付成功后权益能立即生效。
7. 支付失败、取消、重复回调不会导致错发权益。
8. 菜谱审核流程能闭环。
9. 作者可以提交结构化菜谱草稿。
10. 后台能下架违规内容。
11. 第一阶段本地视频文件能迁移到对象存储或新的视频存储方案，迁移后公开视频仍能播放。

十三、第二期风险
1. APP 上架审核风险。
2. iOS IAP 合规风险。
3. Android 多渠道支付差异风险。
4. 用户账号合并错误风险。
5. 支付回调重复和异常风险。
6. 作者上传低质量菜谱风险。
7. 内容审核人力不足风险。
8. 第一阶段账号密码用户绑定微信时，如果身份验证和确认流程不清晰，可能导致账号资产被绑定到错误微信。
9. 视频文件迁移期间，如果元数据和文件路径不一致，可能导致已发布内容无法播放。

十四、第二期补充和修改
1. 当前暂无补充版本。
2. 后续如果第二期需求发生变化，在本章节后追加“第二期 V2.1”“第二期 V2.2”等小版本说明。
3. 每次补充必须写清楚新增内容、修改原因、影响页面、影响接口、验收标准。
