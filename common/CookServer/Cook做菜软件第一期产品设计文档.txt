Cook做菜软件第一期产品设计文档

一、文档说明
1. 本文档只描述 Cook 做菜软件第一期要落地的产品设计。
2. 第一期开完后必须是能简单用起来的版本，不是只能看界面的演示版。
3. 排程算法是本产品核心能力，第一期必须实现简化版排程，不放到第二期。
4. 后续如果第一期需求需要补充或修改，在本文档最后的“第一期补充和修改”章节追加“第一期 V1.1”“第一期 V1.2”等内容。
5. 第二期和第三期分别写在独立 txt 文档中，不放在本文档里。

二、第一期目标
1. 用户打开微信小程序后，可以浏览菜谱内容。
2. 用户可以把菜谱加入菜单，像点外卖一样选择本顿饭要做的菜。
3. 用户每增加或删除一道菜，小程序可以展示整顿饭总耗时和操作时间。
4. 用户点击开始做菜后，可以看到服务端排好的做菜时间线。
5. 用户可以按做菜执行页的步骤提醒完成一顿饭。
6. 第一版需要支持暂停、继续、完成当前、跳过当前。
7. 第一版需要有真实登录注册链路。用户未登录时先进入登录页，用户可以手动注册账号、密码和昵称。
8. 注册账号必须全局唯一，昵称只作为展示名，可以重复。
9. 注册成功后用户可以使用账号和密码登录，登录成功后进入首页。
10. 登录成功后，用户信息、金币、元宝、每日签到、广告奖励、收藏、常用菜单、做菜历史、已拥有菜谱、已购买菜谱、自定义菜谱、个性化菜谱和视频发布记录都跟服务端 userId 绑定。
11. 第一版需要支持用户创建自己的自定义菜谱，把每个要做的事情、步骤耗时和步骤依赖配置进去。
12. 第一版需要支持用户把系统菜谱或别人菜谱改成自己的个性化版本，例如禁用“洗胡萝卜切胡萝卜”，或者把洗菜 1 分钟改成 2 分钟。
13. 第一版需要支持用户把自己的菜谱微调参数分享给其他用户，其他用户可以加载到自己的菜谱里。
14. 第一版需要支持视频内容和菜谱教程绑定。只有作者授权绑定了菜谱教程的视频，左下角才显示加入菜谱的小勺子入口。
15. 第一版需要支持金币购买和元宝购买，但不做人民币充值接口。金币通过签到和广告任务获得，元宝第一期默认赠送。
16. 第一版需要支持作者发布视频、录制菜谱教程、更新菜谱版本，以及购买者在购买版本、作者最新版本、个性化版本之间切换。
17. 第一版需要支持关注作者、基础留言消息、视频分享和微调分享。
18. 第一版视频发布必须是真实调用摄像头录制、真实上传到服务端、真实保存视频文件，不允许只做演示界面。
19. 第一版菜谱教程创建必须是真实上传到服务端，由服务端生成唯一 recipeId，并持久化保存。
20. 第一版结构化云端数据使用 MySQL 保存，视频文件保存到服务端文件目录，MySQL 只保存视频元数据和文件路径。
21. 第一版服务端需要能同时服务微信小程序、Android APP、iOS APP 的 HTTP JSON 接口，虽然第一期只先接微信小程序。

三、第一期用户价值
1. 对新手。
   1. 不需要自己判断先做什么后做什么。
   2. 不需要记住每一步什么时候放什么。
   3. 能看到详细到洗菜、切菜、浸泡、开火、调味、收汁的步骤。
   4. 做菜时有明确提醒，降低做菜焦虑。
2. 对熟手。
   1. 能快速知道一顿饭多久能做好。
   2. 能把米饭、浸泡、炖煮、煮汤等等待时间利用起来。
   3. 能减少忘记做饭、忘记切葱、忘记关火这种低级遗漏。
3. 对产品验证。
   1. 验证用户是否愿意按时间线做菜。
   2. 验证“总耗时”和“操作时间”是否对用户选菜有帮助。
   3. 验证小程序是否适合作为第一入口。

1. 必须实现。

   2. 菜谱公开页和详细页。
   3. 菜单选择页。
   4. 计划预览页。
   5. 做菜执行页。
   6. 音色选择页。
   7. 我的页。
   8. 消息页基础能力。
   9. 自定义菜谱发布页。
   10. 服务端菜谱配置加载。
   11. 服务端排程算法。
   12. 菜谱个性化微调。
   13. 做菜过程中的步骤加时、提前完成和实际耗时记录。
   14. 微调参数分享和加载。
   15. 每日签到、广告倒计时领金币、金币不足弹窗。
   16. 金币菜谱购买、元宝菜谱购买、购买区展示。
   17. 作者视频发布、菜谱教程绑定、视频左下角加入菜谱小勺子入口。
   18. 作者菜谱版本管理、购买者版本更新、同步到个性化。
   19. 做菜结束后的结果记录和视频/照片发布入口。
   20. 关注作者、留言消息、消息免打扰和视频分享。
   21. 服务端账号状态、金币、元宝、签到、广告奖励、收藏、常用菜单、做菜历史、已拥有菜谱、已购买菜谱、自定义菜谱、菜谱个性化配置。
   22. CookServerTest 黑盒测试。
   23. 真实摄像头录制、视频文件上传、服务端视频文件保存和 videoId 生成。
   24. 菜谱教程上传、服务端 recipeId/revisionId 生成和 MySQL 持久化。
   25. 登录页、注册页、账号唯一性校验、密码登录和登录态校验。
2. 第一版实现深度可以简化，但链路必须真实可用。
   1. 推荐流必须能播放真实视频文件。系统内容可以先使用服务端预置的真实视频文件，用户发布视频必须真实上传到服务端保存。
   2. 评论第一期做基础真实评论列表和提交，数据写入 MySQL；可以不做楼中楼、富文本、复杂排序和完整审核。
   3. 发布必须能创建自己的菜谱，也必须能发布视频；第一期用户视频可以进入推荐流，但不做复杂推荐算法。
   4. 语音可以先保留男声和女声选择，优先保证文字提醒。
   5. 真实人民币充值第一期不做，元宝充值接口不做；金币和元宝只做第一期产品内虚拟余额和内测购买流程。
3. 第一版不做。
   1. 真实微信支付。
   2. 真实用户提现。
   3. 真实作者收益。
   4. 大规模视频云存储、视频转码、CDN 分发和完整内容审核系统。
   5. 完整内容审核后台。
   6. 完整好友关系和私信。
   7. 复杂推荐算法。
   8. 企业级分布式高可用。
   9. 用户自定义菜谱的真实公开售卖、真实提现和平台分成。

六、全局界面规则
1. 底部导航固定在页面底部，所有页面内容底部必须留出安全区，避免被手机系统手势条遮挡。
2. 主按钮使用高亮色，次按钮使用弱样式或描边样式。
3. 每个异步操作必须有 loading 状态，例如加入菜单、刷新、开始做菜、收藏、保存菜谱、应用微调。
4. 所有错误必须有用户能理解的提示，不允许只在控制台输出错误。
5. 做菜流程中的安全提醒必须比普通提醒更醒目。
6. 页面内不要出现人民币充值、提现、VIP、去 APP 购买等真实交易相关文案。
7. 第一期开启金币、元宝和菜谱内测购买能力，但所有文案必须表达为产品内虚拟权益，不承诺提现和人民币兑换。
8. 用户对菜谱的修改必须明确区分“修改自己的版本”和“修改原菜谱”。第一期普通用户只能修改自己的个性化版本，不能直接覆盖系统菜谱或别人原始菜谱。
9. 所有个性化记录默认关闭。用户第一次要保存实际耗时时，需要弹出说明并让用户主动开启。
10. 金币和元宝属于两种不同账户余额。金币来自签到和广告任务，元宝第一期默认赠送 100 个，不提供充值入口。
11. 人民币和元宝的关系按 1:10 设计，但第一期只作为后续充值换算规则保留，不在页面展示人民币充值入口。
12. 除登录、注册、健康检查和公开视频资源读取外，其余涉及用户资产和个人数据的接口必须校验登录态。
13. 客户端不能明文长期保存用户密码，只保存服务端返回的登录 token 和必要的账号展示信息。
14. 密码输入框必须使用密码模式展示，注册和登录失败时提示原因，但不能泄露别人的账号是否存在以外的敏感信息。

七、首页信息流界面设计
1. 页面整体。
   1. 顶部固定频道栏，高度约 44px。
   2. 频道从左到右为：推荐、精选、关注、好友。
   3. 当前频道文字加粗，下方显示短横线。
   4. 顶部频道栏背景半透明或浅色，不能挡住内容文字。
   5. 中间为内容区，推荐频道支持上下滑动切换内容。
   6. 底部显示五个导航入口。
2. 推荐频道内容布局。
   1. 每条内容占满一屏。
   2. 背景为视频、图片组或服务端预置的真实视频文件。
   3. 内容左下角放作者头像、作者名、菜名、简介、时间信息和菜谱操作按钮。
   4. 内容右侧中部放竖向操作按钮。
   5. 左下角文案区域最大宽度不超过屏幕 70%，避免和右侧按钮重叠。
   6. 左下角最下方距离底部导航至少 20px。
3. 左下角信息区。
   1. 第一行显示作者头像和作者名，例如“@系统菜谱”。
   2. 第二行显示菜名，例如“糖醋排骨”。
   3. 第三行显示简介，最多两行，超过省略。
   4. 第四行显示“预计 X 分钟 · 动手 Y 分钟”。
   5. 第五行显示操作按钮。
   6. 作者头像右下角显示加号按钮，点击后关注作者；已关注后加号消失或变成已关注状态。
4. 左下角按钮。
   1. “查看菜谱”按钮放在左侧。
   2. 如果作者授权视频绑定菜谱教程，右侧显示小勺子图标按钮，表示“加入菜谱”。
   3. 如果作者没有授权或没有绑定菜谱教程，不显示小勺子图标，也不显示加入菜谱按钮。
   4. 如果菜谱已加入本顿菜单，右侧按钮显示“已加入”。
   5. 按钮高度固定，文字超长时不能撑破按钮。
5. “查看菜谱”点击逻辑。
   1. 点击后进入菜谱详情页。
   2. 已拥有菜谱进入后可看到完整步骤。
   3. 暂未开放菜谱进入后只看到公开信息，不展示购买入口。
   4. 点击时按钮进入 loading 状态，避免重复跳转。
6. “加入菜单”点击逻辑。
   1. 如果菜谱已拥有且未加入菜单，点击小勺子后加入本顿菜单。
   2. 加入成功后显示 toast：“已加入本顿菜单”。
   3. 按钮文案变为“已加入”。
   4. 如果菜谱已加入，再次点击跳转菜单页，并定位到该菜。
   5. 如果菜谱未购买，需要先判断价格类型。
   6. 金币足够时，弹出确认框：“消耗 X 金币加入菜谱？”。
   7. 元宝足够时，弹出确认框：“消耗 X 元宝加入菜谱？”。
   8. 金币不足时，弹出金币不足弹窗，引导用户观看广告领取 30 金币。
   9. 元宝不足时，第一期只提示“元宝不足，充值功能后续开放”，不跳转充值。
   10. 加入菜谱成功后停留在当前视频界面，不自动切换到菜单页。
7. 右侧操作按钮。
   1. 从上到下为点赞、评论、收藏。
   2. 每个按钮为圆形或图标按钮。
   3. 按钮下方显示数量或状态文字。
   4. 点击点赞后按钮高亮，点赞数加一。
   5. 再次点击点赞后取消高亮，点赞数减一。
   6. 点击评论后弹出评论面板。
   7. 点击收藏后切换收藏状态，并同步到我的收藏。
8. 评论面板。
   1. 从底部弹出，高度约屏幕 60%。
   2. 顶部左侧标题为“评论”。
   3. 顶部右侧为关闭按钮。
   4. 内容区显示公开评论列表。
   5. 如果无评论，显示空状态：“还没有评论”。
   6. 第一版需要支持基础真实评论提交。
   7. 评论输入框固定在面板底部，输入为空时发送按钮置灰。
   8. 只有登录用户可以提交评论。
   9. 提交成功后评论立即出现在列表顶部或底部，按当前页面排序规则展示。
   10. 提交失败时保留输入内容，提示用户重试。
   11. 第一版评论可以不支持楼中楼、图片、表情包和富文本。
   12. 公开视频评论和购买后菜谱评分评论需要区分，第一版先做公开视频评论，做过后的评分评论保留数据结构和入口。
9. 精选频道。
   1. 精选频道为卡片列表，不使用全屏沉浸滑动。
   2. 每张卡片固定高度。
   3. 卡片上方显示菜图或视频截图。
   4. 卡片下方显示菜名、简介、预计时间、操作时间、评分。
   5. 点击卡片进入菜谱详情。
10. 关注频道。
   1. 如果用户未关注任何作者，显示空状态。
   2. 空状态文案：“关注作者后，这里会显示他们的新菜谱”。
   3. 空状态按钮：“去推荐看看”，点击切回推荐频道。
   4. 第一版需要实现基础关注关系，关注后作者新视频和新菜谱可以出现在关注频道。
11. 好友频道。
   1. 如果没有好友，显示空状态。
   2. 空状态文案：“互相关注后，可以看到好友做过的菜”。
   3. 第一版可以不实现真实好友动态。
12. 刷新按钮。
   1. 底部左下角 tab 为刷新入口。
   2. 在首页点击刷新当前频道内容。
   3. 在其他页面点击时，先回到首页，再刷新推荐内容。
   4. 刷新过程中显示 loading，不影响底部其他 tab。

八、菜单页界面设计
1. 页面整体。
   1. 顶部为搜索框。
   2. 搜索框下方为左右两栏。
   3. 左侧为分类栏。
   4. 右侧为菜谱列表。
   5. 底部为购物车横条，只有已选菜时显示。
2. 搜索框。
   1. 固定在顶部。
   2. 输入提示文案：“搜索菜谱、食材、分类”。
   3. 输入时实时过滤菜谱。
   4. 搜索结果为空时，右侧显示“没有找到相关菜谱”。
   5. 搜索框右侧显示清除按钮，点击清空关键词。
3. 左侧分类栏。
   1. 分类顺序为：最喜欢、购买区、创作区、蔬菜、荤菜、小荤、饮品、主食、甜品、汤类。
   2. 当前分类背景高亮，左侧显示色条。
   3. 点击分类后右侧列表切换到对应分类。
   4. “最喜欢”展示用户收藏或常用菜。
   5. “购买区”展示用户已经用金币或元宝加入的菜谱。
   6. “创作区”展示用户自己创建的自定义菜谱。
   7. 如果用户还没有创建菜谱，创作区显示空状态和“去创建菜谱”按钮。
   8. 已购买菜谱除了出现在购买区，也要按自身分类分散出现在蔬菜、荤菜、主食等分类下。
4. 右侧菜谱卡片。
   1. 左侧为封面图或封面色块。
   2. 封面左上角显示空心五角星。
   3. 点击空心五角星后变为实心五角星，并把该菜复制到“最喜欢”栏目。
   4. 再次点击实心五角星后取消最喜欢。
   5. 中间上方为菜名。
   6. 菜名右侧或下方显示状态，例如“可做”“金币菜谱”“元宝菜谱”“暂未开放”。
   7. 中间第二行显示简介，最多两行。
   8. 中间第三行显示“预计 X 分钟 · 动手 Y 分钟”。
   9. 标签区显示“新手可做”“可并行”“守火”等标签。
   10. 右侧为加减按钮或暂未开放状态。
   11. 如果该菜谱使用了用户个人版本，卡片上显示“个人版本”标签。
   12. 如果是用户自己创建的菜谱，卡片上显示“我的创作”标签。
5. 加号按钮。
   1. 位置：菜谱卡片右下角。
   2. 未选择且已拥有时为可点击状态。
   3. 点击后该菜加入本顿菜单。
   4. 加入后加号变灰不可点。
   5. 加入后减号变成可点击。
   6. 点击后立刻刷新底部横条，并请求服务端计算排程。
6. 减号按钮。
   1. 位置：加号左侧。
   2. 未选择时灰色不可点。
   3. 已选择时可点。
   4. 点击后从本顿菜单移除。
   5. 移除后重新请求服务端计算排程。
7. 未加入或暂未开放状态。
   1. 未加入但可购买菜谱不显示加号，显示“加入”按钮。
   2. 金币菜谱点击“加入”后走金币扣减逻辑。
   3. 元宝菜谱点击“加入”后走元宝扣减逻辑。
   4. 金币不足时弹出观看广告领金币弹窗。
   5. 元宝不足时提示元宝不足，第一期不提供充值入口。
   6. 暂未开放菜谱显示弱状态标签“暂未开放”。
   7. 点击暂未开放菜谱后进入菜谱详情公开页。
   8. 暂未开放菜谱详情页不展示购买入口，只提示后续开放。
8. 底部购物车横条。
   1. 位置：屏幕底部，位于 tabBar 上方。
   2. 高度固定，左右留边距。
   3. 左侧显示“已选 N 道菜”。
   4. 中间显示“总 X 分钟 · 动手 Y 分钟”。
   5. 右侧主按钮显示“开始做菜”。
   6. 如果正在计算排程，中间显示“正在计算时间...”。
   7. 如果排程失败，右侧按钮置灰，中间显示失败原因。
   8. 点击左侧或中间区域展开购物车面板。
   9. 点击“开始做菜”进入计划预览页。
9. 购物车面板。
   1. 从底部弹出，高度约屏幕 50%。
   2. 背景显示半透明遮罩。
   3. 顶部左侧标题为“本顿菜单”。
   4. 顶部右侧按钮为“收起”。
   5. 列表展示已选菜。
   6. 每行显示菜名、单菜预计时间、操作时间和删除按钮。
   7. 底部显示整顿饭总耗时和操作时间。
   8. 底部右侧再次提供“开始做菜”按钮。
   9. 点击遮罩或“收起”关闭面板。

九、菜谱详情页界面设计
1. 页面整体。
   1. 顶部为封面图或视频。
   2. 封面左上角为返回按钮。
   3. 封面右上角为收藏按钮。
   4. 封面下方为菜名、作者、难度、标签。
   5. 再下方为时间概览、食材、工具、步骤、评论。
   6. 页面底部固定操作栏。
2. 公开信息区。
   1. 显示菜名。
   2. 显示作者。
   3. 显示一句简介。
   4. 显示适合场景，例如“工作日晚餐”“新手可做”“可并行”。
   5. 显示评分、做过人数和评论数。
3. 时间概览区。
   1. 横向显示三个指标。
   2. 第一个为“预计 X 分钟”。
   3. 第二个为“动手 Y 分钟”。
   4. 第三个为“自由 Z 分钟”。
   5. 如果是单菜，还可以显示“适合与米饭/汤并行”。
4. 食材区。
   1. 标题为“准备食材”。
   2. 每行显示食材名和用量。
   3. 食材区应在步骤前展示，方便用户决定是否能做。
   4. 第一版不做购物或食材购买入口。
5. 工具区。
   1. 标题为“需要工具”。
   2. 展示炒锅、砧板、菜刀、电饭锅、汤锅等。
   3. 如果缺少某工具，后续可用于排程限制，第一版先展示。
6. 步骤区。
   1. 已开放菜谱展示完整步骤。
   2. 暂未开放菜谱展示公开信息和后续开放提示。
   3. 每个步骤显示步骤名、详细说明、持续时间。
   4. 每个步骤显示标签：动手、等待、可暂停、不可暂停、可离开、留意厨房。
   5. 安全步骤显示醒目的“注意”标签。
   6. 每个步骤右侧显示“调整”按钮。
   7. 点击“调整”后进入菜谱个性化编辑页，并定位到该步骤。
   8. 如果该菜谱已经存在用户个性化版本，步骤区顶部显示提示：“正在使用你的个人版本”。
   9. 用户可以点击“查看原版”临时对比原始步骤。
7. 个性化操作区。
   1. 位置在时间概览区下方、食材区上方。
   2. 如果用户还没有个性化版本，显示按钮“调整我的做法”。
   3. 如果用户已有个性化版本，显示按钮“编辑我的版本”“恢复原版”“分享微调”。
   4. 点击“调整我的做法”进入菜谱个性化编辑页。
   5. 点击“恢复原版”弹出确认框，确认后删除当前用户对该菜谱的个性化配置。
   6. 点击“分享微调”进入微调分享确认页。
8. 底部操作栏。
   1. 已开放且未加入菜单时，左侧按钮为“加入菜单”，右侧按钮为“开始做菜”。
   2. 已开放且已加入菜单时，左侧按钮为“已加入”，右侧按钮为“去菜单”。
   3. 暂未开放时，左侧按钮为“收藏”，右侧按钮为“暂未开放”且不可点击。
   4. 点击“加入菜单”后留在详情页，显示 toast。
   5. 点击“开始做菜”后，用当前单菜生成排程并进入计划预览页。
   6. 点击“去菜单”后进入菜单页，并保持当前选择。
   7. 点击“暂未开放”不跳转购买，只显示 toast：“该菜谱后续开放”。
9. 暂未开放提示。
   1. 标题为“暂未开放”。
   2. 内容说明该菜谱当前只展示公开信息，第一期暂不开放购买。
   3. 底部按钮为“知道了”。
   4. 关闭后停留在当前菜谱详情页。

十、计划预览页界面设计
1. 页面来源。
   1. 从菜单页点击“开始做菜”进入。
   2. 从菜谱详情点击“开始做菜”进入。
2. 顶部导航。
   1. 左上角为返回按钮。
   2. 中间标题为“本顿做菜计划”。
   3. 右上角为音色按钮。
3. 时间概览卡片。
   1. 顶部大字显示“预计 X 分钟吃上”。
   2. 下方显示“动手 Y 分钟 · 自由 Z 分钟 · 边角 W 分钟”。
   3. 如果本顿有安全步骤，显示提醒：“有明火步骤，请留意提醒”。
4. 时间线区域。
   1. 横向时间轴从 0 分钟开始，到总耗时结束。
   2. 每道菜使用不同颜色。
   3. 主动操作步骤为实色块。
   4. 等待步骤为浅色块。
   5. 未开始时整条时间线为预览状态。
   6. 点击某个时间块，下方显示该步骤详情。
5. 步骤摘要列表。
   1. 按开始时间从早到晚排列。
   2. 每项显示开始时间、菜名、步骤名、持续时间。
   3. 安全步骤显示“注意”标识。
   4. 可离开厨房的等待步骤显示“可离开”。
6. 底部操作区。
   1. 左侧按钮为“返回改菜”。
   2. 右侧主按钮为“开始做菜”。
   3. 点击“返回改菜”回到菜单页，不清空已选菜。
   4. 点击“开始做菜”保存计划到本地并进入做菜执行页。

十一、做菜执行页界面设计
1. 顶部进度区。
   1. 顶部第一行显示“预计剩余 X 分钟”。
   2. 右上角显示当前音色按钮，例如“女声”。
   3. 第二行是总进度条。
   4. 进度条左侧显示已用时间。
   5. 进度条右侧显示总时间。
2. 时间线播放区。
   1. 横向可滚动，样式类似剪辑软件时间线。
   2. 已完成部分变成彩色。
   3. 未开始部分为灰色。
   4. 当前步骤有高亮边框。
   5. 当前时间指针从左向右移动。
3. 当前步骤卡片。
   1. 页面中部展示，视觉优先级最高。
   2. 顶部小字显示“当前步骤”。
   3. 大字显示步骤名。
   4. 显示所属菜。
   5. 显示详细说明。
   6. 显示倒计时。
   7. 显示标签：需要动手、等待计时、可暂停、不可暂停、可离开厨房、留意厨房。
   8. 危险步骤使用醒目颜色，并显示安全提示。
   9. 倒计时右侧显示“加时”入口。
   10. 点击“加时”后弹出加时面板，默认提供“+30 秒”“+1 分钟”“+2 分钟”“自定义”。
   11. 加时不是暂停，点击加时后当前步骤继续执行，只是把当前步骤结束时间向后延长，并同步调整后续步骤和剩余时间。
   12. 如果开启了个性化记录，本次加时后的实际耗时可作为该步骤下次默认耗时的参考。
4. 下一步提醒区。
   1. 当前步骤下方显示“下一步”。
   2. 显示下一步开始时间和准备动作。
   3. 如果下一步需要提前准备，提前 30 秒显示提醒。
5. 后续步骤列表。
   1. 显示接下来 3 到 5 个步骤。
   2. 每项显示时间点、菜名、步骤名、持续时间。
   3. 已完成步骤置灰。
6. 底部控制栏。
   1. 左侧按钮为“提前完成”。
   2. 中间主按钮为“暂停指导”或“继续”。
   3. 右侧按钮为“跳过”。
   4. 控制栏固定在底部。
   5. 点击“暂停指导”后，可暂停步骤停止推进，不可暂停步骤继续倒计时。
   6. 点击“继续”后，根据真实时间刷新当前步骤和剩余步骤。
   7. 点击“提前完成”后，如果当前步骤未到结束时间，也标记完成并推进到下一步，同时把节省的时间从当前计划中扣除。
   8. 点击“跳过”后弹出确认框，文案为“跳过可能影响成品，确认跳过当前步骤吗？”。
7. 个性化耗时记录。
   1. 第一次做菜时默认不自动记录用户实际耗时。
   2. 做菜执行页右上角或完成页提供“记录我的做菜速度”开关。
   3. 用户开启后，系统才把加时、提前完成和真实用时写入该用户的个性化菜谱配置。
   4. 记录后，下次该用户选择同一道菜时，服务端排程使用用户个性化耗时。
   5. 用户可以在菜谱详情页恢复原版耗时。
   6. 如果用户没有开启记录，本次加时和提前完成只影响当前正在执行的计划，不影响下次默认时长。
8. 完成页。
   1. 所有步骤完成后显示“本顿饭完成”。
   2. 显示计划总耗时、实际总耗时。
   3. 显示本次和计划相比提前或延迟了多少时间。
   4. 如果用户未开启个性化记录，显示开关：“以后按我的实际速度优化时间”。
   5. 显示按钮：评分、收藏本顿组合、秀一秀、再做一次。

十二、音色选择页界面设计
1. 页面从计划预览页或做菜执行页右上角进入。
2. 左上角为返回按钮。
3. 页面标题为“选择播报音色”。
4. 主体显示男声、女声两个选项。
5. 当前选中的音色显示勾选标识。
6. 点击某个音色立即保存。
7. 如果有试听能力，每个音色右侧显示“试听”按钮。
8. 第一版如果暂时没有真实语音，可以保存选择并在页面上保留状态。

十三、发布入口和自定义菜谱界面设计
1. 底部中间 + 进入发布类型选择页。
2. 发布类型选择页提供两个主入口：蓝色“分享”和红色“创作”。
3. 蓝色“分享”用于录制普通视频，红色“创作”用于创建带步骤、耗时、依赖和排程属性的菜谱教程。
4. 第一版发布页必须能创建用户自己的菜谱教程。
5. 第一版创建出的菜谱教程默认进入用户自己的创作区；只有绑定到用户发布的视频后，才通过视频进入推荐流。
6. 页面顶部。
   1. 左上角为返回按钮。
   2. 中间标题为“创建菜谱”。
   3. 右上角为“保存草稿”按钮。
7. 基础信息区。
   1. 菜名输入框，必填，输入提示文案为“菜名，例如番茄炒蛋”。
   2. 分类选择器，必填，选项包括蔬菜、荤菜、小荤、饮品、主食、甜品、汤类、其他。
   3. 简介输入框，选填，用于公开页和菜单列表展示。
   4. 难度选择，选项为新手可做、普通、进阶。
   5. 封面选择，第一期可以选择图片，也可以用默认色块。
8. 食材区。
   1. 标题为“准备食材”。
   2. 每行包含食材名和用量两个输入框。
   3. 每行右侧有删除按钮。
   4. 底部有“添加食材”按钮。
   5. 食材顺序按用户填写顺序保存。
9. 工具区。
   1. 标题为“需要工具”。
   2. 使用多选标签，例如炒锅、汤锅、砧板、菜刀、电饭锅、水槽、碗。
   3. 底部有“添加自定义工具”按钮。
10. 步骤编辑区。
   1. 标题为“做菜步骤”。
   2. 每个步骤是一张可折叠卡片。
   3. 卡片折叠状态显示步骤序号、步骤标题、耗时、是否动手。
   4. 卡片展开后显示完整编辑项。
   5. 每个步骤必须填写标题、详细说明、持续时间。
   6. 每个步骤必须选择资源，例如 user、sink、board、stove、rice_cooker、pot。
   7. 每个步骤必须选择是否需要持续动手。
   8. 每个步骤必须选择是否可暂停。
   9. 每个步骤必须选择暂停期间是否继续。
   10. 每个步骤必须选择是否可离开厨房。
   11. 每个步骤必须选择安全级别。
   12. 每个步骤可选择依赖步骤。
   13. 每个步骤可填写语音播报文本。
11. 步骤操作按钮。
   1. 每个步骤卡片右上角有删除按钮。
   2. 每个步骤卡片底部有“上移”“下移”“复制”按钮。
   3. 步骤列表底部有“添加步骤”按钮。
   4. 对已经保存过的步骤点击删除后，步骤卡片置灰并显示“已删除”，不从列表中直接消失。
   5. 已删除步骤右上角显示“恢复”按钮，点击后恢复该步骤。
   6. 新增但尚未保存的步骤可以直接移除。
   7. 如果删除步骤会影响其他步骤依赖，弹出确认框。
12. 预估时间区域。
   1. 固定显示在步骤编辑区下方。
   2. 显示当前菜谱预计总时长和操作时长。
   3. 用户每次修改步骤后，前端或服务端重新计算单菜预估。
   4. 如果步骤缺少必填项，显示“完善步骤后计算时间”。
13. 底部操作栏。
   1. 左侧按钮为“保存草稿”。
   2. 右侧主按钮为“保存并加入我的菜谱”。
   3. 点击“保存草稿”只保存未完成菜谱，不出现在菜单可做列表。
   4. 点击“保存并加入我的菜谱”前必须校验必填字段。
   5. 保存成功后，该菜出现在菜单页“创作区”。
14. 发布到推荐流。
   1. 第一版菜谱教程发布后先进入用户自己的创作区。
   2. 用户发布普通视频时，可以选择绑定某个已发布菜谱教程。
   3. 绑定教程的视频可以进入推荐流。
   4. 进入推荐流的视频左下角显示小勺子加入菜谱入口。
   5. 没有绑定教程的视频可以进入推荐流，但不显示小勺子。
   6. 第一版不做完整公开审核后台，先按内测内容池处理。

十四、菜谱个性化编辑页界面设计
1. 页面用途。
   1. 用户可以基于系统菜谱、别人分享的菜谱或自己的菜谱，调整出适合自己的做法。
   2. 个性化修改不覆盖原菜谱。
   3. 对系统菜谱和别人菜谱的个性化配置跟随当前用户账号。
   4. 菜谱名称和基础 recipeId 仍然保持原菜谱不变，但服务端给该用户下发时会合并个人微调层。
2. 页面入口。
   1. 菜谱详情页点击“调整我的做法”。
   2. 菜谱详情页某个步骤点击“调整”。
   3. 做菜完成页点击“按本次耗时优化”。
   4. 消息页收到别人分享的微调参数后，点击“查看并应用”。
3. 顶部区域。
   1. 左上角为返回按钮。
   2. 中间标题为“调整我的做法”。
   3. 右上角为“保存”按钮。
   4. 标题下方显示提示：“只修改你的个人版本，不影响原菜谱”。
4. 原版对比。
   1. 页面顶部提供“我的版本”和“原版”切换。
   2. 默认进入“我的版本”。
   3. 点击“原版”时只读展示原始步骤，不允许编辑。
   4. 点击“我的版本”回到可编辑状态。
5. 食材微调。
   1. 用户可以标记某个食材已经预处理。
   2. 例如胡萝卜可以标记为“已买胡萝卜丁”。
   3. 标记后，相关的洗胡萝卜、切胡萝卜步骤可以被建议禁用。
   4. 用户也可以手动禁用或保留这些步骤。
   5. 被禁用的原菜谱步骤不能从列表里消失，只能置灰显示，并提供恢复入口。
6. 步骤微调。
   1. 每个步骤以卡片展示。
   2. 卡片左侧显示步骤顺序。
   3. 卡片中间显示步骤标题、说明、时长。
   4. 卡片右侧显示开关“本次保留”。
   5. 关闭“本次保留”表示该步骤在用户个人版本中禁用。
   6. 禁用后的步骤仍留在列表原位置，整张卡片置灰，标题旁显示“已禁用”。
   7. 置灰卡片右侧显示“恢复”按钮，点击后重新启用该步骤。
   8. 禁用步骤后，如果其他步骤依赖它，系统要提示依赖影响。
   9. 被禁用步骤不参与排程，不计入总耗时和操作时间。
   10. 用户可以修改步骤标题。
   11. 用户可以修改步骤说明。
   12. 用户可以修改步骤时长。
   13. 用户可以修改是否可暂停、是否可离开厨房和安全级别。
7. 时长调整。
   1. 每个步骤时长右侧提供减号、加号和输入框。
   2. 减号每次减少 30 秒，不能小于 0。
   3. 加号每次增加 30 秒。
   4. 点击输入框可以直接输入分钟和秒。
   5. 修改后页面底部实时刷新单菜预计时间和操作时间。
8. 添加个人步骤。
   1. 步骤列表底部有“添加个人步骤”按钮。
   2. 新增步骤只属于当前用户个人版本。
   3. 新增步骤需要填写标题、说明、时长、资源、是否动手、是否可暂停、是否可离开厨房。
   4. 新增步骤可以设置依赖步骤。
   5. 用户新增的个人步骤可以真正删除，因为它不是原菜谱内容。
   6. 删除个人新增步骤前需要弹出确认框。
9. 重排步骤。
   1. 每个步骤提供“上移”“下移”按钮。
   2. 调整顺序时不能破坏依赖关系。
   3. 如果调整后依赖不合法，系统提示并阻止保存。
10. 底部操作栏。
   1. 左侧按钮为“恢复原版”。
   2. 中间按钮为“保存草稿”。
   3. 右侧主按钮为“保存我的版本”。
   4. 点击“恢复原版”弹出确认框。
   5. 点击“保存我的版本”后，服务端保存该用户对该 recipeId 的个性化配置。
   6. 保存成功后返回菜谱详情页，并显示“正在使用你的个人版本”。

十五、微调分享和加载界面设计
1. 功能定位。
   1. 用户可以把自己的菜谱微调参数分享给其他用户。
   2. 分享的是微调参数，不是覆盖原菜谱。
   3. 接收方加载后，会生成接收方自己的个人版本。
2. 分享入口。
   1. 菜谱详情页点击“分享微调”。
   2. 菜谱个性化编辑页保存后点击“分享给朋友”。
   3. 做菜完成页如果本次实际耗时形成了新个人版本，可以点击“分享我的调整”。
3. 分享确认页。
   1. 顶部显示菜名。
   2. 显示本次微调摘要，例如“禁用 2 个步骤，调整 3 个步骤时长，新增 1 个个人步骤”。
   3. 显示预计总耗时和操作时间变化。
   4. 显示可分享对象：好友、复制分享码、生成分享卡片。
   5. 第一版如果好友体系不完整，可以先支持生成分享码或通过消息页模拟发送。
4. 接收消息。
   1. 消息页出现一条“某用户分享了菜谱微调”。
   2. 消息卡片显示菜名、分享者、耗时变化摘要。
   3. 卡片右侧按钮为“查看并应用”。
5. 加载确认页。
   1. 顶部显示“应用菜谱微调”。
   2. 显示原菜谱名称。
   3. 显示对方微调了哪些步骤。
   4. 显示应用后预计时间变化。
   5. 底部左侧按钮为“取消”。
   6. 底部右侧按钮为“应用到我的菜谱”。
   7. 点击应用后，不覆盖原菜谱，只写入当前用户的个人版本。
6. 冲突处理。
   1. 如果用户本来已有个人版本，应用前必须提示：“这会覆盖你当前的个人调整，是否继续？”。
   2. 如果原菜谱版本不一致，提示“该分享基于旧版菜谱，可能存在步骤不一致”。
   3. 如果某些步骤已经不存在，只应用仍能匹配的步骤，其余步骤列为失败项。

十六、消息页界面设计
1. 顶部标题为“消息”。
2. 页面分区为系统通知、微调分享、评论、点赞、关注。
3. “微调分享”是第一期需要支持的消息类型。
4. 第一版如果没有真实好友体系，可以通过 userId 或分享码模拟给另一个用户发送微调消息。
5. 微调分享消息卡片。
   1. 左侧显示分享者头像或默认头像。
   2. 中间显示“某用户分享了一个菜谱微调”。
   3. 下一行显示菜名和耗时变化摘要。
   4. 右侧按钮为“查看”。
   5. 点击“查看”进入微调加载确认页。
6. 系统通知。
   1. 展示服务端下发的基础通知。
   2. 点击后可以展开通知详情。
7. 空状态。
   1. 如果没有任何消息，显示“还没有消息，做完一道菜后可以来看看反馈”。
   2. 空状态下不显示无意义按钮。

1. 顶部账号区。
   1. 左侧为头像。
   2. 中间为昵称和用户 ID。
   3. 右侧为设置按钮。
2. 账号概览区。
   1. 显示已收藏菜谱数量。

   3. 显示常用菜单数量。
   4. 显示已开放菜谱数量。
   5. 显示金币余额。
   6. 显示元宝余额。
   7. 显示今日是否已签到。
   8. 第一版不显示人民币充值按钮，不提供元宝充值入口。
3. 菜谱资产区。
   1. “我的收藏”。
   2. “已开放菜谱”。
   3. “我的发布”。
   4. “常用菜单”。
   5. “我的个性化菜谱”。
   6. “我的视频”。
   7. 点击“我的发布”进入自己创建的菜谱列表。

十八、第一期排程算法设计
1. 算法目标。
   1. 在保证依赖顺序和厨房安全的前提下，尽量把等待时间用于其他可执行步骤。
   2. 输出用户能理解的整顿饭时间线。
   3. 同时输出总耗时、操作时间、自由时间和边角时间。
2. 输入。
   1. recipeIds：用户本顿选择的菜谱 ID。
   2. 每道菜的 tasks。
   3. 每个 task 的 durationSeconds。
   4. 每个 task 的 dependencies。
   5. 每个 task 的 resource。
   6. 每个 task 的 active。
   7. 每个 task 的 canPause。
   8. 每个 task 的 continuesDuringPause。
   9. 每个 task 的 canLeaveKitchen。
   10. 每个 task 的 safetyLevel。
   11. 用户对菜谱的个性化微调配置。
   12. 用户自定义菜谱。
   13. 用户是否开启个性化耗时记录。
3. 第一阶段资源模型。
   1. user：用户本人，同一时刻只能进行一个 active=true 的持续操作。
   2. sink：水槽。
   3. board：砧板和刀。
   4. stove：燃气灶或炒锅。
   5. rice_cooker：电饭锅。
   6. pot：汤锅。
   7. 第一阶段默认单灶、单水槽、单砧板。
4. 步骤类型。
   1. 主动操作步骤：active=true，占用 user。
   2. 等待步骤：active=false，不占用 user，但可能占用 stove、rice_cooker、pot。
   3. 短动作步骤：持续时间很短，但会打断自由时间，例如开大火、加调料。
   4. 安全等待步骤：active=false，但 safetyLevel 为 attention 或 danger。
5. 排程规则。
   1. 服务端排程前先加载基础菜谱。
   2. 如果当前用户存在该 recipeId 的个性化微调配置，先把基础菜谱和个人微调配置合并成用户有效菜谱。
   3. 如果用户选择的是自定义菜谱，直接使用该用户创建的菜谱步骤。
   4. 被用户禁用的原菜谱步骤仍保留在个性化配置中，但不进入排程。
   5. 被用户修改过时长的步骤使用用户个性化时长。
   6. 用户新增的个人步骤进入排程。
   7. 依赖未完成的步骤不能开始。
   8. active=true 的步骤同一时刻只能安排一个。
   9. 相同 resource 同一时刻默认不能重复占用。
   10. active=false 的等待步骤可以和 active=true 的操作步骤并行。
   11. 米饭、浸泡、炖煮、煮汤等等待类步骤应尽早启动。
   12. 安全级别为 danger 的 stove 步骤不安排用户离开厨房。
   13. 如果两个步骤都可做，优先安排能开启长等待的步骤。
   14. 如果两个步骤耗时相近，优先安排依赖链更长的菜。
   15. 如果用户当前有 1 到 3 分钟空档，默认计入边角时间。
   16. 第一阶段采用贪心排程，不做复杂全局最优。
6. 时间统计。
   1. totalSeconds：最后一个步骤结束时间。
   2. activeSeconds：所有 active=true 步骤的持续时间求和。
   3. freeSeconds：连续可离开厨房且时长超过阈值的等待时间总和。
   4. edgeSeconds：不可稳定利用的短等待时间总和。
   5. 第一阶段 freeBlock 阈值建议为 5 分钟，低于 5 分钟默认算边角时间。
7. 输出。
   1. summary：总耗时、操作时间、自由时间、边角时间和摘要。
   2. selectedRecipes：本顿选择的菜。
   3. timeline：按开始时间排序的步骤。
   4. freeBlocks：可自由利用的时间段。
   5. warnings：安全提醒和排程限制说明。
   6. personalizationApplied：是否应用了用户个性化菜谱配置。
   7. personalizationSummary：本次使用了哪些个人微调，例如禁用步骤、恢复步骤、改时长、新增步骤。
8. 暂停处理。
   1. 用户暂停时，客户端记录暂停开始时间。
   2. canPause=true 的当前主动步骤停止推进。
   3. continuesDuringPause=true 的等待步骤继续推进。
   4. 恢复时，客户端根据当前真实时间重新判断哪些等待步骤已完成。
   5. 如果恢复后某个关键提醒已过期，立即提示用户处理。
9. 加时和提前完成处理。
   1. 加时只延长当前步骤，不等于暂停。
   2. 加时后，当前步骤结束时间后移，后续依赖步骤顺延。
   3. 提前完成会立即结束当前步骤，后续可开始步骤重新判断。
   4. 如果当前步骤是等待步骤且不可暂停，提前完成需要二次确认，避免用户错误结束实际等待。
   5. 如果用户开启个性化耗时记录，本次实际耗时写入用户个人菜谱配置。
   6. 如果用户未开启个性化耗时记录，本次实际耗时只影响当前计划。
10. 中途开始处理。
   1. 第一版可以先做简化实现。
   2. 用户可勾选已经完成的步骤。
   3. 客户端把已完成步骤传给服务端。
   4. 服务端把剩余步骤重新排程。
11. 示例。
   1. 糖醋排骨洗肉 2 分钟。
   2. 排骨浸泡 10 分钟。
   3. 浸泡期间安排淘米 5 分钟。
   4. 浸泡期间安排洗葱切葱 3 分钟。
   5. 浸泡剩余 2 分钟计入边角时间。
   6. 炒排骨 5 分钟。
   7. 炖煮 25 分钟计入自由时间。
   8. 开大火 5 分钟可作为等待或轻提醒。
   9. 最后翻炒收汁 5 分钟计入操作时间。

十九、菜谱结构和 MySQL 存储
1. 菜谱结构来源和运行时存储。
   1. 菜谱制作流程仍然使用结构化 JSON 表达，便于版本兼容、人工检查和导入导出。
   2. 系统初始菜谱可以继续放在 CookServer.exe 同级目录下的 res/recipes，作为种子 JSON 文件。
   3. 服务端启动或后台导入时，把 res/recipes 里的种子 JSON 导入 MySQL。
   4. 第一阶段运行时以 MySQL 为准，接口下发菜谱、账号拥有关系、作者菜谱版本和个性化配置时不再直接依赖本地 JSON 文件。
   5. 用户创作菜谱不写回 res/recipes，而是直接写入 MySQL。
   6. JSON 文件必须使用 UTF-8。
2. 版本号。
   1. 每个单菜 JSON 根对象必须包含 schemaVersion。
   2. schemaVersion 描述菜谱制作流程 JSON 结构版本，不是 APP 版本或服务端版本。
   3. 当前第一阶段使用 "1.0"。
3. 菜谱基础字段。
   1. id：菜谱唯一 ID。
   2. title：菜名。
   3. category：菜单分类。
   4. subtitle：公开页和推荐流简介。
   5. difficulty：难度。
   6. coverColor 或 coverImage：封面展示。
   7. author：作者。
   8. tags：标签。
   9. ingredients：食材列表。
   10. tools：工具列表。
   11. defaultOwned：新账号是否默认拥有。
   12. systemRecipe：是否系统菜谱。
   13. tasks：做菜步骤。
4. 步骤字段。
   1. id：菜谱内步骤短 ID。
   2. title：步骤标题。
   3. detail：详细操作说明。
   4. resource：占用资源。
   5. durationSeconds：持续秒数。
   6. active：是否需要用户持续操作。
   7. canPause：是否可暂停。
   8. continuesDuringPause：暂停期间是否自然继续。
   9. canLeaveKitchen：是否可离开厨房。
   10. safetyLevel：安全等级。
   11. dependencies：依赖步骤。
   12. voiceText：语音播报文本。
5. 用户自定义菜谱。
   1. 用户自定义菜谱也使用同一套菜谱结构。
   2. 自定义菜谱 ID 由服务端生成，建议使用 user_cook_ 开头或其他能区分系统菜谱的稳定 ID。
   3. 自定义菜谱归属于创建用户。
   4. 第一版自定义菜谱默认只对创建用户可见。
   5. 自定义菜谱出现在菜单页“创作区”和我的页“我的发布”。
6. 菜谱个性化配置。
   1. 个性化配置不是完整复制一份菜谱，而是保存用户相对原菜谱的修改。
   2. 个性化配置按 userId + recipeId 保存。
   3. 原 recipeId 不变，菜名不变，但服务端给该用户下发时合并个人配置。
   4. 个性化配置可以包含禁用原菜谱步骤、恢复原菜谱步骤、修改步骤时长、修改步骤说明、新增个人步骤、调整依赖。
   5. 个性化配置可以记录用户实际耗时，但必须在用户开启个性化记录后才写入。
   6. 用户可以删除整份个性化配置并恢复原版菜谱。
   7. 被用户禁用的原菜谱步骤必须保留记录，不能物理删除，以便用户随时恢复。
7. 微调分享配置。
   1. 分享内容只包含微调参数，不包含付费权益，也不改变原菜谱归属。
   2. 分享配置需要记录 baseRecipeId、baseSchemaVersion、baseRecipeRevision、分享者 userId、微调摘要和具体修改项。
   3. 接收方应用分享配置后，会在自己的账号下生成一份个性化配置。
   4. 如果原菜谱版本不匹配，应用前必须提示用户。
8. 第一阶段云端存储方案。
   1. 第一阶段服务端必须真实持久化用户数据，不能只存在内存中。
   2. 账号、密码摘要、昵称、金币、元宝、签到状态、广告奖励记录、拥有菜谱、购买区、最喜欢、个性化菜谱、作者菜谱、菜谱版本、关注关系、留言、评论、做菜历史和做菜结果发布记录都存入 MySQL。
   3. MySQL 表内保存稳定业务 ID，例如 userId、recipeId、revisionId、videoId、messageId、commentId。
   4. 服务端生成 ID 时必须保证唯一性，建议使用业务前缀加递增序号或雪花 ID 思路，例如 user_000001、video_000001、user_cook_000001、revision_000001。
   5. 密码不能明文保存，MySQL 中只保存带盐哈希后的密码摘要和盐值。
   6. 视频文件不直接存入 MySQL 大字段。
   7. 用户上传的视频文件保存到服务端文件目录，建议根目录为 CookServer.exe 同级目录下的 data/videos/files。
   8. 视频文件建议按日期和 userId 分目录保存，例如 data/videos/files/2026/08/user_000001/video_000001.mp4。
   9. MySQL 只保存 videoId、userId、文件相对路径、文件大小、时长、封面路径、绑定 recipeId、发布时间和状态。
   10. 如果后续接入对象存储或 CDN，只需要把视频文件存储层从本地目录替换为对象存储，业务表仍保存 videoId 和访问地址。
   11. txt 文件不再作为第一期正式业务存储，只允许作为导入导出、人工备份或调试报告使用。

二十、服务端接口要求
1. POST /api/auth/register。
   1. 用于用户手动注册账号。
   2. 入参包含 account、password、nickname。
   3. account 必须全局唯一。
   4. nickname 允许重复。
   5. 注册成功后服务端生成 userId，初始化金币、元宝、默认菜谱权益和账号配置。
   6. 注册成功后可以直接返回登录 token，也可以让客户端跳转登录页重新登录；第一期建议直接返回 token 并进入首页。
2. POST /api/auth/login。
   1. 用于账号密码登录。
   2. 入参包含 account、password。
   3. 登录成功返回 userId、account、nickname、token、tokenExpireTime 和账号摘要信息。
   4. 登录失败返回明确但安全的错误提示，例如“账号或密码错误”。
3. POST /api/auth/logout。
   1. 用于退出登录。
   2. 服务端可使当前 token 失效。
   3. 客户端清理本地 token 和账号快照后回到登录页。
4. GET /api/auth/session。
   1. 用于客户端启动时校验本地 token 是否仍然有效。
   2. token 有效时返回账号摘要和钱包摘要。
   3. token 无效时客户端回到登录页。
5. GET /api/health。
   1. 用于检查服务是否启动。
   2. 返回服务名、版本、IP、端口。
6. GET /api/feed。
   1. 返回推荐流内容。
   2. 返回推荐、精选、关注、好友四个 tab 数据。
7. GET /api/recipes。
   1. 返回菜谱列表、分类和账号拥有状态。
   2. 客户端根据 owned 决定是否展示加入菜单。
   3. 返回给用户时，如果该菜谱存在个人微调配置，需要包含个性化后的预计时间和 personalizationApplied 标记。
8. GET /api/account。
   1. 返回用户基础资料、账号、昵称、金币、元宝、签到状态、收藏、常用菜单、做菜历史、已开放菜谱、自定义菜谱数量和个性化记录开关。
   2. 该接口必须校验登录 token，并按 token 中的 userId 查询数据。
9. POST /api/account/profile。
   1. 修改用户资料。
   2. 第一期允许修改昵称。
   3. account 不允许修改。
10. POST /api/account/password。
   1. 修改密码。
   2. 入参包含 oldPassword 和 newPassword。
   3. 修改成功后建议使旧 token 失效，客户端重新登录。
11. POST /api/favorites/toggle。
   1. 入参为 recipeId。
   2. 返回最新收藏状态。
12. POST /api/recipes/custom/save。
   1. 保存用户自定义菜谱。
   2. 入参为菜谱基础信息、食材、工具、步骤。
   3. 草稿可以允许部分字段为空。
   4. 保存并加入我的菜谱时必须校验必填字段和步骤依赖。
13. POST /api/recipes/custom/publish。
   1. 发布用户自定义菜谱教程。
   2. 入参为完整菜谱结构。
   3. 服务端保存到 MySQL，返回 recipeId 和 revisionId。
14. POST /api/recipes/personalization/save。
   1. 保存用户对某个菜谱的个性化微调。
   2. 入参为 recipeId 和微调配置。
   3. 不覆盖原始菜谱。
15. POST /api/recipes/personalization/reset。
   1. 删除当前用户对某个菜谱的个性化微调。
   2. 入参为 recipeId。
   3. 删除后该用户重新使用原版菜谱。
16. POST /api/recipes/personalization/share。
   1. 生成或发送用户的微调分享。
   2. 入参为 recipeId、目标 userId 或分享方式。
   3. 返回 shareId 或消息发送结果。
17. POST /api/recipes/personalization/apply。
   1. 接收方应用别人分享的微调配置。
   2. 入参为 shareId。
   3. 应用后生成当前用户自己的个性化配置。
18. POST /api/account/personalization/setting。
   1. 设置是否开启个性化耗时记录。
   2. 默认关闭。
19. POST /api/cook/task/actual-time。
   1. 上报某个步骤本次实际耗时。
   2. 入参为 planId、recipeId、taskId、actualSeconds、finishType。
   3. finishType 可表示正常完成、加时完成、提前完成、跳过。
   4. 只有用户开启个性化记录时，服务端才把实际耗时写入个性化配置。
20. POST /api/plan/preview。
   1. 入参为 recipeIds。
   2. 服务端需要使用当前用户的个性化菜谱和自定义菜谱参与排程。
   3. 返回 summary、selectedRecipes、timeline、freeBlocks、personalizationApplied、personalizationSummary。
21. POST /api/plan/start。
   1. 入参为 recipeIds。
   2. 返回 planId 和完整计划。
   3. 客户端拿到完整计划后本地执行。
   4. 返回计划中必须标记每个步骤是否来自原菜谱、用户微调或用户新增步骤。
22. 第一阶段新增接口。
   1. 金币、元宝、签到、广告奖励、视频发布、视频绑定菜谱、作者版本更新、关注、留言和做菜结果发布都属于第一期接口范围。
   2. 详细接口清单见“二十三、18. 第一阶段新增接口要求”。
23. 文件上传接口要求。
   1. 视频上传接口必须接收真实视频文件，服务端保存成功后返回 videoId、访问地址、封面地址或封面生成状态。
   2. 菜谱教程发布接口必须接收完整菜谱结构，服务端保存成功后返回 recipeId 和 revisionId。
   3. 上传和发布接口必须在写入 MySQL 元数据成功后才返回成功。
   4. 如果文件保存成功但元数据保存失败，服务端需要返回失败并记录日志，不能让客户端以为发布成功。
   5. 第一阶段可以不做断点续传、转码、多清晰度和 CDN，但不能省略真实上传和持久化。
24. 接口鉴权和用户归属。
   1. 除 /api/auth/register、/api/auth/login、/api/health、公开视频文件读取外，其余接口必须携带登录 token。
   2. 服务端必须从 token 解析 userId，不能信任客户端请求体里的 userId。
   3. 如果某个接口需要操作目标用户，例如发送留言给 targetUserId，只能把 targetUserId 当作目标对象，不能当作当前登录用户。
   4. token 无效、过期或账号被禁用时，统一返回未登录或登录过期状态，客户端回到登录页。
   5. 涉及金币、元宝、拥有菜谱、个性化菜谱、视频发布、关注和留言的写接口必须记录操作者 userId。
25. 钱包和权益一致性。
   1. 金币和元宝余额变化必须记录流水。
   2. 每条流水包含 transactionId、userId、currencyType、changeAmount、beforeAmount、afterAmount、reason、relatedId、createTime。
   3. 每日签到、广告奖励、金币加入菜谱、元宝加入菜谱都必须写流水。
   4. 加入菜谱接口需要支持 idempotencyKey，客户端重复提交同一次请求时不能重复扣金币或元宝。
   5. 扣减余额和写入拥有菜谱关系必须在同一数据库事务里完成。
   6. 余额不足时不能写入拥有菜谱关系。
   7. 已经拥有的菜谱再次加入时不能重复扣费，只能返回已拥有状态。
26. 评论、点赞和收藏接口。
   1. POST /api/comments/list 获取视频或菜谱公开评论列表。
   2. POST /api/comments/create 提交评论。
   3. POST /api/likes/toggle 点赞或取消点赞视频。
   4. POST /api/favorites/toggle 收藏或取消收藏视频、菜谱。
   5. 评论、点赞和收藏都必须绑定当前登录 userId。
   6. 点赞和收藏接口需要幂等，重复点击只切换当前用户自己的状态。

   4. timeline 按时间排序。
   5. 依赖步骤不会出现在依赖完成之前。

   7. 恢复某个已禁用步骤后，该步骤重新进入排程。

   4. 加时后当前步骤结束时间和后续步骤顺延。
   5. 提前完成能跳到下一步。
   6. 未开启个性化记录时，本次加时不影响下次默认时长。

   6. 服务端不能崩溃、死锁、卡死。
5. 真机测试。
   1. 微信开发者工具模拟器能运行。
   2. 真机预览能运行。
   3. 体验版二维码能给体验成员打开。
   4. 如果未配置 HTTPS 合法域名，需记录“打开调试才能访问”的限制。

二十二、第一期验收标准
1. 至少 5 个体验用户完成一次真实做菜流程。
2. 至少 3 个用户认为总耗时和操作时间有帮助。
3. 至少 3 个用户认为步骤提醒降低做菜焦虑。
4. 糖醋排骨和米饭组合能正确展示并行排程。
5. 做菜执行页能按时间线推进，暂停和继续可用。
6. 用户能创建一份自己的自定义菜谱，并把它加入菜单生成排程。
7. 用户能把系统菜谱调整成自己的个人版本，例如禁用某个预处理步骤或修改步骤时长。
8. 被禁用的原菜谱步骤在编辑页置灰显示，并能一键恢复。
9. 用户能在做菜过程中加时和提前完成，并在开启个性化记录后影响下次默认时长。
10. 用户能把自己的微调参数分享给另一个用户，另一个用户能加载到自己的菜谱里。
11. 服务端压力测试通过。
12. 小程序没有明显页面乱码、按钮遮挡、文字溢出和无法返回的问题。
13. 用户能完成注册和登录，重复账号不能注册，重复昵称允许注册。
14. 登录后所有个人资产和个人内容都跟当前账号绑定，切换账号后不能看到另一个账号的私有数据。
15. 服务端重启后，账号、钱包、拥有菜谱、创作菜谱和个性化配置仍然存在。
16. 首页推荐流能正常刷视频，无菜谱绑定的视频不显示小勺子。
17. 有菜谱绑定且作者授权的视频显示小勺子，点击后能加入菜单并停留在视频页。
18. 金币菜谱能通过金币加入，金币不足时能进入模拟广告倒计时流程。
19. 广告倒计时未满 30 秒退出不发金币，倒计时满 30 秒后发放 30 金币。
20. 元宝默认赠送 100 个，元宝菜谱能扣减元宝后进入购买区。
21. 菜单页五角星能把菜谱加入或移出“最喜欢”。
22. 底部中间 + 能进入发布类型选择页，并提供蓝色“分享”和红色“创作”两个入口。
23. 用户能发布普通视频，也能创建带步骤的菜谱教程。
24. 作者更新菜谱后，购买者能看到步骤更新入口，并能同步到作者最新版或个性化版本。
25. 单菜时间条能按 60 分钟一行展示，步骤多或超过 60 分钟时不超出屏幕。
26. 做菜执行页能展示时间条进度、当前步骤填充进度、加时、跳过和语音播报。
27. 自由时间结束时能播放小程序内部闹铃提醒。
28. 单菜完成后能询问是否按本次实际耗时更新个性化，多菜完成后不自动同步个性化。
29. 做菜结束后能选择视频或照片记录结果，并发布到我的页创作列表。
30. 视频界面能关注作者，消息页能发送留言，互关和非互关的提示音默认状态符合设计。
31. 钱包流水能追踪签到、广告奖励、金币扣减和元宝扣减。
32. 重复提交同一次购买或加入菜谱请求不会重复扣费。
33. 服务端重启后账号、余额、拥有菜谱、创作菜谱、个性化配置、视频元数据和评论仍然存在。
34. 超出大小或格式不支持的视频上传会失败，并且不会产生可见的脏数据。
35. hidden 状态的视频、菜谱和评论不会出现在公开推荐和公开详情里。

二十三、第一期新增功能详细需求
1. 视频流和加入菜谱。
   1. 首页推荐流必须能正常刷视频，第一期可以使用用户真实录制上传的视频或服务端预置的真实视频文件。
   2. 视频左下角只有在作者授权并绑定菜谱教程时，才显示加入菜谱的小勺子图标。
   3. 没有绑定菜谱教程的视频不显示小勺子图标，用户只能点赞、收藏、评论或关注作者。
   4. 点击小勺子后，如果菜谱已拥有，则直接加入用户自己的菜单，不切换页面。
   5. 点击小勺子后，如果菜谱需要金币或元宝，则先校验余额。
   6. 金币或元宝扣减成功后，该菜谱加入用户菜单，并进入对应分类和购买区。
   7. 加入成功后仍停留在当前视频页，只显示 toast：“已加入菜单”。
2. 金币和元宝。
   1. 金币是任务货币，只能通过每日签到和观看广告获得。
   2. 元宝是充值货币，人民币和元宝按 1:10 设计。
   3. 第一阶段不做元宝充值接口，不出现人民币支付入口。
   4. 第一阶段新用户默认赠送 100 元宝。
   5. 金币和元宝需要在账号页展示余额。
   6. 金币菜谱只能用金币加入。
   7. 元宝菜谱只能用元宝加入。
   8. 元宝购买后的菜谱显示在购买区，也按菜谱分类显示到蔬菜、荤菜、主食等分类下。
3. 每日签到。
   1. 我的页或任务入口显示“每日签到”。
   2. 用户每天第一次点击签到，默认获得 5 金币。
   3. 当天已经签到后，按钮显示“今日已签到”，不可重复领取。
   4. 签到状态按自然日记录，服务端以服务器时间为准。
4. 观看广告领金币。
   1. 默认观看广告奖励为 30 金币。
   2. 第一阶段不接真实广告 SDK，使用内部模拟广告页。
   3. 金币不足且用户点击加入菜谱、购买金币菜谱等购买按钮时，弹出金币不足弹窗。
   4. 弹窗文案说明：“金币不足，是否观看 30 秒广告领取 30 金币？”。
   5. 弹窗左侧按钮为“取消”，点击后关闭弹窗并停留当前页面。
   6. 弹窗右侧按钮为“观看广告”，点击后进入广告倒计时页。
5. 模拟广告页。
   1. 页面中心显示 30 秒倒计时。
   2. 倒计时从 30 到 0，每秒减少 1。
   3. 页面可以用一个本地制作的倒计时视频或前端倒计时动画模拟广告。
   4. 右上角显示关闭按钮。
   5. 用户在倒计时完成前点击关闭，弹出确认框：“当前未看满 30 秒，返回将无法获得金币，确认返回吗？”。
   6. 用户确认返回后回到原页面，不发金币。
   7. 用户取消返回后继续广告倒计时。
   8. 当用户点击关闭并停留在确认框时，广告倒计时暂停。
   9. 当用户把小程序切到后台或切换到其他程序时，广告倒计时暂停。
   10. 用户回到小程序后，从暂停秒数继续倒计时。
   11. 倒计时到 0 后，自动发放 30 金币，并显示“金币已到账”。
   12. 发放成功后返回触发金币不足弹窗的原页面。
6. 菜单页最喜欢。
   1. 菜谱卡片左上角显示空心五角星。
   2. 用户点击空心五角星后，五角星变实心。
   3. 被点亮的菜谱复制进入“最喜欢”栏目。
   4. 再次点击实心五角星后，从“最喜欢”栏目移除。
   5. “最喜欢”只是用户常用入口，不改变菜谱原分类。
7. 发布入口。
   1. 底部中间加号点击后，进入发布类型选择页。
   2. 发布类型选择页只有两个主按钮。
   3. 蓝色按钮为“分享”，用于录制和发布普通视频。
   4. 红色按钮为“创作”，用于录制或编辑一套带步骤的做菜教程。
8. 蓝色分享流程。
   1. 点击蓝色“分享”后真实调用微信小程序摄像头能力，开始录制完整视频。
   2. 录制完成后进入视频预览页，预览页播放本地刚录制的视频文件。
   3. 视频预览页右上角显示“发布”按钮。
   4. 发布前用户可以选择是否附上自己创作过的菜谱教程。
   5. 点击发布后，客户端必须把真实视频文件上传到服务端。
   6. 服务端保存视频文件，生成 videoId，并把视频元数据写入 MySQL。
   7. 服务端返回成功后，客户端才显示发布成功。
   8. 如果视频文件上传失败或服务端元数据写入失败，客户端必须提示发布失败，并允许用户重试。
   9. 如果选择附上菜谱教程，别人刷到该视频时，视频左下角显示小勺子加入菜谱图标。
   10. 如果不选择菜谱教程，该视频不显示小勺子图标。
   11. 发布成功后，视频进入用户自己的创作区，并能在我的页“我的视频/创作”中看到。
9. 红色创作流程。
   1. 点击红色“创作”后进入做菜教程编辑页。
   2. 默认生成流程：选材、清洗、浸泡、开火、下锅、放入调料或者加水、炖煮、收汁、出锅。
   3. 用户可以手动添加流程。
   4. 用户可以删除流程；删除后步骤置灰，不直接消失，并可恢复。
   5. 每个流程都需要填写步骤名。
   6. 步骤名是文本框，点击后弹出输入法。
   7. 每个流程都需要填写分钟和秒。
   8. 每个流程都需要标记步骤类型。
   9. 步骤类型至少包括“动手操作”和“可离开等待”。
   10. 步骤类型用圆点加文字显示，放在同一行，交互类似单选题。
   11. 用户点击一个圆点后，另一个圆点自动取消。
   12. 底部显示“发布”按钮。
   13. 点击发布后，客户端必须把完整菜谱教程结构上传到服务端。
   14. 服务端生成全局唯一 recipeId 和首个 revisionId。
   15. 服务端把菜谱教程和版本信息写入 MySQL。
   16. 服务端返回成功后，客户端才显示发布成功。
   17. 如果菜谱教程保存失败，客户端必须提示失败，并保留本地编辑内容供用户重试。
   18. 发布成功后，菜谱进入菜单页“创作区”，也能在我的页“我的发布”中找到。
10. 作者更新和菜谱版本。
   1. 作者可以修改自己已经发布的菜谱。
   2. 每次修改都生成一个新版本，不覆盖历史版本。
   3. 作者可以查看自己的所有历史修改记录。
   4. 购买者默认只能看到购买时版本。
   5. 如果作者发布了新版本，购买者在菜谱详情页右上方看到“步骤更新”按钮。
   6. 点击“步骤更新”后，购买者的作者版本更新到作者最新版本。
   7. 如果已经是最新版，则不显示按钮，显示文字“当前已是最新版”。
   8. 购买者只能拥有三类版本：购买时版本、作者最新版本、个性化版本。
   9. 作者版本页需要有“同步到个性化”按钮。
   10. 点击“同步到个性化”后，把当前作者版本复制成用户自己的个性化版本。
   11. 当用户存在个性化版本时，后续点菜和排程默认使用个性化版本。
11. 单菜时间条。
   1. 每个菜谱详情和做菜执行页都需要展示单菜时间条。
   2. 时间条必须能完整显示在屏幕宽度内，不能横向超出屏幕。
   3. 时间条以 60 分钟为一整条。
   4. 如果总时长超过 60 分钟，时间条换行显示第二条、第三条。
   5. 每个步骤在时间条上用黑色竖线分割。
   6. 竖线上方或内部显示简短步骤文字。
   7. 步骤文字空间不足时可以缩写，但底下详细步骤列表必须展示完整内容。
   8. 时间条底下展示具体步骤，每个步骤包含时间、步骤名和详细内容。
12. 做菜执行进度。
   1. 点击开始后，时间条上出现进度指针并开始向前移动。
   2. 底下当前步骤卡片使用深色进度填充，随着当前步骤时间推进逐渐填满。
   3. 倒入调料、撒葱花、加入盐这类短动作，默认时长为 5 秒。
   4. 每个步骤右侧显示“加时”和“跳过”按钮。
   5. 点击“加时”可以延长当前步骤。
   6. 点击“跳过”后当前步骤立即结束，并跳到下一步骤。
   7. 如果做菜已经开始，跳到下一步骤时要立即语音播报下一步要做的事。
13. 空闲结束闹铃。
   1. freeBlock 结束时必须触发软件内部闹铃提醒。
   2. 该闹铃不是手机系统闹钟，而是小程序内部播放的提示音。
   3. 闹铃用于提醒用户从自由时间回到厨房。
   4. 用户回到页面后可以点击“我知道了”停止声音。
14. 单菜执行后的个性化更新。
   1. 在作者版本或个性化版本里单独做一道菜时，系统记录用户跳过的步骤、加时、提前完成和实际执行时间。
   2. 用户全部做完或提前结束时，弹出提示：“是否根据本次实际执行时间更新到个性化版本？”。
   3. 用户点击“是”，则更新个性化版本。
   4. 如果用户当前是在作者版本里做菜，且还没有个性化版本，点击“是”后自动生成个性化版本。
   5. 用户点击“否”，本次记录只保存到做菜历史，不影响下次排程。
   6. 该自动更新能力只在单菜制作时生效。
   7. 如果用户同时做多道菜，只允许加时和跳过，不把实际执行记录自动同步到个性化版本。
   8. 多菜场景下，用户仍然可以进入某个菜的个性化菜单手动修改时长和步骤。
15. 做菜结束后的结果发布。
   1. 做菜结束时自动弹框询问：“是否记录本次做菜结果？”。
   2. 用户可以选择视频模式或照片模式。
   3. 视频模式进入拍摄页，用户拍摄视频、填写配文并发布。
   4. 照片模式允许选择或拍摄照片、填写配文、选择配乐并发布。
   5. 照片后期特效模拟短视频是第二期功能，第一期只做照片、配文、配乐选择的基础链路。
   6. 发布前用户可以选择是否附上本次菜单。
   7. 如果本次菜单里有多道菜，需要让用户逐个勾选要附上的菜。
   8. 发布成功后，视频或照片内容出现在我的页“我的视频/创作”。
16. 我的页视频资产。
   1. 我的页视频资产区分为四项：点赞、收藏、创作、菜单。
   2. 点赞、收藏、创作以视频列表形式展示，交互类似短视频应用的个人主页。
   3. 菜单展示作者发布的带步骤菜单，界面类似外卖点餐列表。
   4. 点击菜单项进入菜单详情页，展示详细步骤、时间条和加入菜单入口。
17. 关注和消息。
   1. 视频界面显示作者头像，头像下方有加号。
   2. 点击加号后关注作者。
   3. 用户关注作者后，可以在消息页选择该作者发送留言。
   4. 第一阶段消息不是强实时聊天，按留言消息处理。
   5. 博主可以选择留言提示音或免打扰。
   6. 默认状态是免打扰。
   7. 如果双方互关，则默认有提示音。
   8. 用户可以长按头像弹出菜单，选择免打扰。
   9. 消息页可以分享视频，分享方式参考短视频应用的私信分享。
18. 第一阶段新增接口要求。
   1. GET /api/account/wallet 返回金币、元宝、签到状态。
   2. POST /api/account/checkin 每日签到领取 5 金币。
   3. POST /api/account/ad-reward/start 创建模拟广告观看记录。
   4. POST /api/account/ad-reward/finish 广告满 30 秒后发放 30 金币。
   5. POST /api/recipes/join 使用金币或元宝加入菜谱。
   6. POST /api/videos/upload 上传真实视频文件，返回 videoId。
   7. POST /api/videos/publish 发布视频元数据。
   8. POST /api/videos/attach-recipe 给视频绑定菜谱教程。
   9. POST /api/recipes/custom/publish 发布用户自定义菜谱教程，返回 recipeId 和 revisionId。
   10. POST /api/recipes/version/publish 作者发布新菜谱版本。
   11. POST /api/recipes/version/update-to-latest 购买者更新到作者最新版。
   12. POST /api/recipes/version/sync-personalization 同步作者版本到个性化版本。
   13. POST /api/follow/toggle 关注或取消关注作者。
   14. POST /api/messages/send 发送留言或分享视频。
   15. POST /api/cook/result/publish 发布做菜结果视频或照片。
   16. POST /api/comments/list 获取评论列表。
   17. POST /api/comments/create 提交评论。
   18. POST /api/likes/toggle 点赞或取消点赞。
19. 第一阶段新增测试要求。
   1. 金币不足时点击加入菜谱能弹出广告引导弹窗。
   2. 广告倒计时未满 30 秒关闭，不发金币。
   3. 广告倒计时切后台后暂停，回到前台后继续。
   4. 广告倒计时满 30 秒后发放 30 金币。
   5. 每日签到一天只能领取一次 5 金币。
   6. 元宝默认 100，元宝菜谱扣减成功后进入购买区。
   7. 无菜谱绑定的视频不显示小勺子。
   8. 有菜谱绑定的视频显示小勺子，点击后能加入菜单。
   9. 作者更新菜谱后，购买者能看到步骤更新按钮。
   10. 购买者同步到作者最新版后，可以再同步到个性化。
   11. 单菜做完后确认更新个性化，下一次排程使用新耗时。
   12. 多菜做完后不自动同步个性化。
   13. 做菜结束后能发布视频或照片，并能在我的页创作列表看到。
   14. 关注作者后能发送留言。
   15. 互关后消息默认有提示音，非互关默认免打扰。
   16. 录制视频后必须能真实上传服务端，并在服务端生成 videoId。
   17. 服务端重启后，已上传视频元数据仍能从 MySQL 恢复。
   18. 发布菜谱教程后必须能真实上传服务端，并在服务端生成 recipeId 和 revisionId。
   19. 服务端重启后，用户创作区里的菜谱教程仍能从 MySQL 恢复。

二十四、第一期登录注册和账号数据设计
1. 入口规则。
   1. 小程序启动时先读取本地 token。
   2. 本地没有 token 时，直接进入登录页。
   3. 本地有 token 时，先调用 /api/auth/session 校验登录态。
   4. token 有效时进入首页。
   5. token 无效、过期或服务端返回账号不存在时，清理本地登录信息并进入登录页。
2. 登录页布局。
   1. 页面顶部显示产品名和一句简短说明。
   2. 中间是账号输入框。
   3. 账号输入框下方是密码输入框，密码必须隐藏显示。
   4. 密码输入框右侧可以提供显示/隐藏密码的小图标。
   5. 输入区下方是主按钮“登录”。
   6. 登录按钮下方左侧是“注册账号”，右侧是“忘记密码”。
   7. 第一阶段可以先不实现找回密码，点击“忘记密码”时提示“第一阶段暂不支持找回，请联系管理员处理”。
   8. 登录请求中按钮进入 loading 状态，禁止重复点击。
3. 登录交互。
   1. 账号或密码为空时，前端直接提示用户补全。
   2. 登录成功后保存 token、userId、account、nickname 到本地缓存。
   3. 登录成功后进入首页，并拉取账号钱包、拥有菜谱和推荐流。
   4. 登录失败时停留登录页，提示“账号或密码错误”。
   5. 网络失败时提示“网络异常，请稍后重试”。
4. 注册页布局。
   1. 页面左上角是返回按钮。
   2. 页面标题为“注册账号”。
   3. 第一项是账号输入框。
   4. 第二项是昵称输入框。
   5. 第三项是密码输入框。
   6. 第四项是确认密码输入框。
   7. 底部主按钮为“注册并登录”。
5. 注册字段规则。
   1. account 是登录账号，必须全局唯一。
   2. account 建议只允许字母、数字、下划线，长度 4 到 32 位。
   3. nickname 是展示昵称，允许重复，长度 1 到 24 个中文字符或等效长度。
   4. password 建议长度至少 6 位，第一阶段可以不强制复杂度，但不能允许空密码。
   5. confirmPassword 必须和 password 一致。
   6. 注册时前端先做基础校验，服务端必须再次校验。
6. 注册成功后的账号初始化。
   1. 服务端生成 userId。
   2. 服务端写入账号基础资料。
   3. 服务端初始化金币余额。
   4. 服务端初始化元宝余额，第一阶段默认 100 元宝。
   5. 服务端根据 systemRecipe/defaultOwned 初始化免费菜谱拥有关系。
   6. 服务端初始化每日签到状态、个性化记录开关、消息免打扰默认值。
   7. 注册成功后返回 token，客户端直接进入首页。
7. 密码和安全。
   1. 密码不能明文保存到 MySQL。
   2. 服务端必须保存带盐哈希后的密码摘要。
   3. 登录校验时使用用户输入密码加同一盐值计算摘要，再和数据库摘要对比。
   4. 日志里不能打印明文密码、密码摘要、token。
   5. token 需要有过期时间。
   6. 第一阶段可以先使用简单 token 表存储，后续再升级 JWT 或更完整的会话系统。
8. MySQL 结构化数据范围。
   1. account 表保存 userId、account、nickname、passwordHash、passwordSalt、createTime、status。
   2. auth_session 表保存 tokenId、userId、tokenHash、expireTime、createTime、status。
   3. wallet 表保存 userId、coins、yuanbao、updateTime。
   4. wallet_transaction 表保存 transactionId、userId、currencyType、changeAmount、beforeAmount、afterAmount、reason、relatedId、idempotencyKey、createTime。
   5. checkin 表保存 userId、checkinDate、rewardCoins。
   6. ad_reward 表保存 rewardId、userId、startTime、finishTime、rewardCoins、status。
   7. recipe 表保存 recipeId、authorUserId、title、category、schemaVersion、currentRevisionId、status。
   8. recipe_revision 表保存 revisionId、recipeId、revisionNumber、recipeJson、createTime。
   9. user_recipe 表保存 userId、recipeId、ownedType、ownedTime、favorite、source、sourceTransactionId。
   10. recipe_personalization 表保存 userId、recipeId、baseRevisionId、personalizationJson、updateTime。
   11. video 表保存 videoId、userId、filePath、coverPath、durationSeconds、bindRecipeId、status、createTime。
   12. comment 表保存 commentId、targetType、targetId、userId、content、createTime、status。
   13. like_state 表保存 targetType、targetId、userId、liked、updateTime。
   14. favorite_state 表保存 targetType、targetId、userId、favorited、updateTime。
   15. follow 表保存 userId、targetUserId、notifyMode、createTime。
   16. message 表保存 messageId、senderUserId、receiverUserId、messageType、contentJson、createTime、readState。
   17. cook_history 表保存 historyId、userId、planJson、resultJson、createTime。
9. 系统菜谱导入 MySQL。
   1. res/recipes/*.json 作为系统菜谱种子文件保留。
   2. 服务端启动时检查 MySQL 中是否已有对应 recipeId。
   3. 如果 MySQL 没有该 recipeId，则导入为系统菜谱。
   4. 如果 MySQL 已有该 recipeId，默认不覆盖，避免线上用户已购买或个性化的数据受到影响。
   5. 后续需要更新系统菜谱时，通过菜谱版本发布流程生成新 revision。
10. 视频文件存储。
   1. 视频文件保存在服务端文件目录，不保存到 MySQL 大字段。
   2. 推荐目录为 CookServer.exe 同级目录下的 data/videos/files。
   3. 文件路径按日期和 userId 分层，避免单目录文件过多。
   4. 文件名使用 videoId 加原始扩展名，例如 video_000001.mp4。
   5. MySQL 保存相对路径、原始文件名、文件大小、时长、封面路径和绑定菜谱 ID。
   6. 删除视频时先把 MySQL 状态改为 deleted，物理文件可由后续清理任务处理。
11. 视频上传限制和失败处理。
   1. 第一阶段支持 mp4 格式优先。
   2. 单个视频最大大小需要服务端配置，建议第一阶段默认 100MB。
   3. 单个视频最长时长需要服务端配置，建议第一阶段默认 5 分钟。
   4. 上传接口必须校验文件扩展名、MIME 类型和实际文件大小。
   5. 服务端保存文件时必须防止路径穿越，客户端上传的文件名不能直接拼接到服务器路径中。
   6. 文件保存成功但 MySQL 写入失败时，需要删除刚保存的临时文件或把文件标记为 orphan，避免长期堆积。
   7. MySQL 写入成功但客户端断线时，客户端重试应通过 idempotencyKey 或 videoId 查询确认，不应重复创建视频。
12. 内容发布状态。
   1. 视频、用户菜谱、评论、留言都必须有 status 字段。
   2. 第一阶段 status 至少包括 draft、published、hidden、deleted。
   3. 用户保存草稿时为 draft。
   4. 用户点击发布且服务端保存成功后为 published。
   5. 运营或管理员需要临时隐藏内容时改为 hidden。
   6. 用户删除自己内容时改为 deleted，不建议立即物理删除。
   7. 推荐流、关注流、我的公开列表只展示 published 内容。
   8. 用户自己的我的页可以展示 draft 和 hidden，但必须清楚标记状态。
13. 第一阶段最小运营处理能力。
   1. 第一阶段可以不做完整后台，但服务端至少要保留按 videoId、recipeId、commentId 把内容改为 hidden 的管理接口或管理命令。
   2. 被隐藏内容不再进入推荐流和公开详情页。
   3. 被隐藏内容如果已经被用户加入菜单，菜单里应提示“该内容已被隐藏，暂不可查看公开页”，但本地已拥有的菜谱执行数据是否可继续使用由服务端状态决定。
   4. 管理隐藏操作必须写日志，记录操作者、目标内容和原因。
14. 为什么第一期直接使用 MySQL。
   1. 账号唯一性、密码登录、金币扣减、元宝扣减、菜谱拥有关系和版本历史都需要可靠一致性。
   2. txt 文件适合配置、导入导出和测试报告，不适合作为多个用户同时写入的正式账号资产存储。
   3. 第一阶段直接使用 MySQL，可以减少后续从 txt 迁移账号资产时的数据一致性风险。
   4. 视频文件仍使用文件系统保存，因为视频体积大，不适合直接写入 MySQL。
