Cook做菜软件第三期产品设计文档

一、文档说明
1. 本文档只描述第三期产品设计。
2. 第三期建立在第一期核心流程验证成功、第二期多端账号和商业化基础跑通的前提下。
3. 第三期重点是平台化、分布式高可用、推荐系统、创作者生态、家庭协作和规模化运营。
4. 如果第三期后续需要补充或修改，在本文档最后的“第三期补充和修改”章节追加“第三期 V3.1”“第三期 V3.2”等内容。

二、第三期目标
1. 从单一做菜工具升级为厨房时间管理平台。
2. 从系统菜谱为主升级为系统菜谱和创作者菜谱共同供给。
3. 从单机服务升级为可横向扩展的分布式服务。
4. 从人工选择菜谱升级为个性化推荐和智能菜单组合。
5. 从单人做饭升级为家庭多人协作。

三、分布式服务端架构
1. API 服务无状态化。
2. 前面使用负载均衡。
3. 多台 CookServer 实例共同承载微信小程序、Android APP、iOS APP 流量。
4. MySQL 存储账号、订单、菜谱、评论、关注、权益、做菜历史。
5. Redis 存储会话、热点菜谱、限流数据、临时解锁权益、分布式锁。
6. 对象存储保存图片和视频。
7. CDN 分发封面、视频、步骤图片。
8. 消息队列处理异步任务，例如视频转码、审核、通知、结算。
9. 搜索服务支持菜名、食材、作者、标签检索。
10. 监控系统覆盖接口耗时、错误率、CPU、内存、队列积压和数据库连接池。

四、高可用要求
1. 任意一台 API 服务器挂掉，不影响整体访问。
2. 菜谱查询和做菜计划生成必须可横向扩展。
3. 支付回调必须幂等。
4. 订单和权益写入必须有事务或可靠补偿。
5. Redis 不可用时，核心已购买权益查询不能完全瘫痪。
6. MySQL 主库异常时，要有备份和恢复策略。
7. 服务端日志、监控、告警、dump 和链路追踪完整。
8. 所有后台任务失败都要可重试。
9. 所有异步消息都要能避免重复消费造成脏数据。

五、推荐系统
1. 推荐目标。
   1. 帮用户更快找到今天能做的菜。
   2. 帮用户组合出省时的一顿饭。
   3. 帮新手避开高失败率菜谱。
   4. 帮优质作者获得曝光。
2. 推荐信号。
   1. 用户收藏。
   2. 用户做过的菜。
   3. 用户评分。
   4. 用户实际完成率。
   5. 用户可用时间。
   6. 用户厨房设备。
   7. 用户口味标签。
   8. 菜谱复做率。
   9. 菜谱投诉率。
3. 推荐结果。
   1. 今日快手菜。
   2. 30 分钟工作餐。
   3. 新手低失败率。
   4. 一菜一饭组合。
   5. 两菜一汤组合。
   6. 用户关注作者新菜。
4. 推荐限制。
   1. 推荐系统不能推荐用户没有条件完成的菜。
   2. 推荐系统不能为了点击率牺牲安全。
   3. 高投诉、高失败率菜谱需要降权。
   4. 新作者内容需要冷启动保护，但不能过度影响用户体验。

六、高级排程
1. 厨房条件配置。
   1. 灶眼数量。
   2. 水槽数量。
   3. 砧板数量。
   4. 是否有电饭锅。
   5. 是否有烤箱。
   6. 是否有空气炸锅。
   7. 是否有微波炉。
   8. 用户切菜速度。
   9. 用户能否接受离开厨房。
2. 排程模式。
   1. 新手模式：步骤更细、提醒更频繁、并行更保守。
   2. 熟手模式：步骤合并、提醒减少、并行更激进。
   3. 安全模式：明火等待尽量不离开厨房。
   4. 省时模式：最大化并行，减少总耗时。
   5. 省心模式：减少同时进行的事情，牺牲少量总时间。
3. 多人协作。
   1. 支持家庭成员分工。
   2. 每个人有自己的任务列表。
   3. 系统提醒谁该做什么。
   4. 如果某个人延迟，整体排程重新计算。
4. 异常处理。
   1. 某一步做慢了。
   2. 某一步提前完成。
   3. 用户临时暂停。
   4. 某个设备不可用。
   5. 食材缺失。
   6. 菜谱步骤失败。

七、创作者生态
1. 作者等级。
   1. 新作者。
   2. 认证作者。
   3. 优质作者。
   4. 专业作者。
2. 作者数据。
   1. 发布菜谱数。
   2. 完做次数。
   3. 复做率。
   4. 平均评分。
   5. 投诉率。
   6. 收益。
3. 菜谱质量分。
   1. 步骤完整度。
   2. 时间准确度。
   3. 用户成功率。
   4. 用户评分。
   5. 复做率。
   6. 安全投诉。
4. 平台扶持。
   1. 优质作者推荐位。
   2. 高质量菜谱包。
   3. 新手专题。
   4. 工作日晚餐专题。
   5. 节日菜单专题。

八、家庭和社交
1. 家庭菜单。
   1. 家庭成员共享本周菜单。
   2. 支持记录家人口味偏好。
   3. 支持避开不吃的食材。
2. 多人做饭。
   1. 支持两个人同时做饭。
   2. 系统按人分配任务。
   3. 每个人手机显示自己的步骤。
   4. 某个人延迟后重新排程。
3. 好友分享。
   1. 分享本顿菜单。
   2. 分享做菜成果。
   3. 分享菜谱组合。
   4. 好友可以一键加入菜单。
4. 家庭计划。
   1. 本周工作餐计划。
   2. 食材清单汇总。
   3. 买菜清单。
   4. 剩余食材推荐菜。

九、平台商业化
1. 菜谱包。
2. 会员订阅。
3. 广告解锁。
4. 作者付费菜谱。
5. 平台抽成。
6. 品牌合作。
7. 食材和厨具导购。
8. 家庭会员。
9. 企业福利餐计划。

十、风控和合规
1. 内容安全。
   1. 文案审核。
   2. 图片审核。
   3. 视频审核。
   4. 评论审核。
   5. 投诉下架。
2. 交易安全。
   1. 防刷单。
   2. 防重复支付。
   3. 防退款套利。
   4. 防作者收益造假。
3. 广告安全。
   1. 防诱导点击。
   2. 防刷广告。
   3. 防未完成观看发权益。
4. 做菜安全。
   1. 高风险菜谱审核。
   2. 明火和热油步骤强提醒。
   3. 禁止发布危险误导内容。
   4. 涉及健康功效时避免医疗化表述。

十一、第三期验收标准
1. 多客户端 API 行为一致。
2. 高峰请求下服务不崩溃、不死锁、不明显卡死。
3. 任意一台 API 服务器下线，客户端仍能访问服务。
4. 付费、权益、退款、提现有完整对账。
5. 内容审核和投诉处理可闭环。
6. 推荐系统能提升开始做菜转化率。
7. 家庭菜单和多人协作能完成真实做饭场景。

十二、第三期风险
1. 分布式系统复杂度显著上升。
2. 创作者内容质量难以控制。
3. 推荐系统可能推荐不适合用户厨房条件的菜。
4. 支付和提现合规风险变高。
5. 家庭协作对实时同步要求更高。
6. 视频和图片成本上升。
7. 内容审核成本上升。

十三、第三期补充和修改
1. 当前暂无补充版本。
2. 后续如果第三期需求发生变化，在本章节后追加“第三期 V3.1”“第三期 V3.2”等小版本说明。
3. 每次补充必须写清楚新增内容、修改原因、影响页面、影响接口、验收标准。
